# workflow.md — code2course 执行流程详解（第 0–9 步）

本文件是 SKILL.md「执行流程（分步总览）」的完整版。SKILL.md 只保留每步一句话，需要某一步的细节时按小节锚点加载本文件对应内容。**逐步执行，严格按序。**

> **证据纪律（贯穿第 1–4 步）**：所有分析结论必须锚定真实代码中的**文件名 + 函数名/类名/变量名**作为佐证。禁止"应该是"、"大概"式表述——每一个写进课程的说法，学习者都必须能翻到对应代码验证。这也正是测验"解释要指出正确答案背后的代码依据"的来源。

## 第 0 步：询问讲解档位（必问并等确认，随时可切）

在动工前必须先向用户提问选档并等待确认——**禁止默认、猜测或自动选择档位**。档位是**会话级全局参数**，控制全课的讲解精细度、信息密度、分段颗粒度与每模块内容量下限；生成过程中用户可随时切换（规则见本节末尾）。档位只改这四件事，不改其余硬约束。

### 档位参数表

| 维度 | L1 快览档 | L2 标准档 | L3 精讲档 |
|---|---|---|---|
| 定位 | 建立全局心智模型 | 吃透主要流程 | 逐文件逐函数吃透、可动手改 |
| 覆盖范围 | 1 个已验证入口 + 1–2 个最高频流程 | 第 2 步 3–5 个流程族，每族 1 个模块 | 第 2 步 3–5 个流程族，每族拆 2–3 个模块（结构/机制/流程分层） |
| 每模块代码翻译块 | 0–1 个 | ≥2 个（§5 内容量下限） | ≥3 个，每个核心目录/文件至少 1 段逐字代码 |
| 每模块动画/图表 | 1 个 | ≥1 个 | ≥2 个，§3 的 3a–3d 全部落地为内容 |
| 每模块测验 | 0–1 个 | ≥1 个（3+ 选项） | ≥2 个，含"加功能改哪些文件""为什么这样设计"深题 |
| 信息密度 | 低：术语只留核心、隐喻精简、不展开 3a–3d | 中：三层底线 + 关键取舍各 1 处 | 高：3a–3d 全展开、每个取舍给"为什么"、赌注/沙盘等参与式控件更密 |
| 分段颗粒度 | 粗：1–2 段覆盖整课，模块合并为 3–5 屏 | 中：1 模块 = 1 段，过大按组件边界拆（§8.0） | 细：1 模块内按"结构层/机制层/流程层"再分多段 |
| 单/多文件 | 优先单文件 | 按 §9 条件触发 | 内容量大，更易满足 §9 拆分条件 |

> 表内数量是**该档位的最低要求/上限指引**；三档之间在讲解深度、信息密度、分段数量上必须拉开明显差距，禁止"三档都写成一样"。
>
> 档位数量下限同时是**机检事实源**：`validate_course.py --tier L1|L2|L3` 内置同表数值（脚本为准，本表为人读版）。"动画/图表 ≥N" 的计数口径 = 引擎组件（data-viz 三类 + 五个参与式控件场景）+ 手绘 SVG 图组。

### 选档与切档规则

1. **选档（激活时，必问）**：动工前必须主动向用户提问"用哪个档位：①快览档 ②标准档 ③精讲档？"并**等待用户确认**后才进入第 1 步。即使用户请求里已含档位词（"用快览档/标准档/精讲档""快速概览/精讲/逐行详解"等），也要复述确认（如"确认用精讲档，对吗？"），不得凭字面默认、猜测或自动选档；在收到明确确认前**不得开跑**。两条放宽：①**快速通道**——用户同一条消息里既有明确档位词、又有明确的开始指令时，复述确认后即可开跑，不必再空等一轮（用户随时可打断纠正）；②**角色桥接**——提问时可顺带问一句读者身份（audience.md 四画像），按其「角色 → 档位建议」对照表给建议，但**用户拍板，不代选**。
2. **切档（生成中，随时）**：用户明确说"切到精讲档/切回快览档"等即生效；若用户只说"太细了/再详细点/简单点"等**未指明目标档位**，必须先问清切到哪一档，不得猜测。切换后：
   - **未生成的段**：立即按新档位重新规划分段粒度与每段深度（更新 §8.0 拼接清单）。
   - **已生成的段**：升档（L1→L2、L2→L3 等）时按新档位**重写**补足深度与组件；降档（L3→L2 等）时按新档位**合并精简**（删次要组件、合并模块/段）。切换时向用户一句话说明调整范围。
   - 切换**不推倒重来**：已完成的代码分析（第 1–4 步产物）与三张表（第 2.5 步）复用，只按新档位增减讲解深度与分段，不重新侦察仓库。
   - **重写代价确认**：切档涉及 ≥3 段或多册的重写/精简时，先向用户报一句预估改动范围（"约 5 屏要按精讲档回炉"），确认后再动手；小范围切换直接执行并一句话说明。
3. **档位只影响深度与分段**：代码逐字复制（含转义铁律）、隐喻唯一、数字可溯源、零依赖、外壳来自 resources、测验应用型等其余硬约束不因档位而变；讲解精细度、信息密度、分段颗粒度与每模块内容量下限随档位缩放——L1 允许低于 §5 标准下限，L3 要求高于标准下限。
4. **交付前复核档位一致性**：最终全课（含已重写段）的翻译块/测验/动画数量与分段粒度须与最终档位相符，无"前半精讲后半快览"的割裂（见 quality-gates.md）。
5. **冲突裁决规则（唯一优先级，防止两份刚性清单打架）**：通用内容下限条款（SKILL.md「视觉覆盖」、§5「每模块内容量下限」、quality-gates.md 对应验收项）与档位参数表冲突时，**一律以档位参数表为准**——L1 允许每模块 0–1 翻译块、0–1 测验、只 1 种交互元素；而零依赖、代码逐字（含转义）、隐喻唯一、数字可溯源、外壳来自 resources 等**完整性约束不接受任何档位豁免**。

## 第 1 步：物理拓扑与入口点映射

### 1a. 目录与依赖分层

- 浏览目录结构，识别主要语言、框架、构建工具
- 读 package.json / requirements.txt / go.mod 等依赖清单，并把核心依赖分两类：
  - **运行时强依赖**（缺了就跑不起来，如数据库驱动、Web 框架）
  - **可替换抽象层**（只是接口适配，换掉不影响核心逻辑，如某 LLM SDK、某云厂商 SDK）
- 这一层分类直接决定封面目录职责导览图怎么画、以及"换供应商要改哪里"类测验的答案

### 1b. 启动入口拓扑

- 列出**所有**可能的启动方式（Web 页面、CLI 命令、定时任务、Webhook 服务、CI Action……），不止第一个发现的
- 为每种方式标注对应入口文件，并**逐个验证**：
  - Web 应用：从 `index.html` / `main.*` / `app.*` 实际追到挂载点或启动调用，确认它真的被构建工具引用
  - CLI 工具：从 package.json 的 `bin` 字段或 argparse 入口确认
  - API 服务：从启动脚本（如 `server.js`、`manage.py runserver`）确认
  - 验证方法：入口文件中必须能找到"启动/挂载"的实际调用语句；找不到就换候选，直到闭环
- 确定这是"什么类型的应用"，以及**用户最可能从哪个入口进入**（它是课程第一模块的主角）

## 第 2 步：找出 3–5 个最常见的用户操作流程

问自己：真实用户打开这个应用后，最常做的 3–5 件事是什么？
例如：提交一个表单、加载一个列表页面、登录、搜索、点击某个按钮。
每个流程就是课程的一个候选模块。

**大纲轻确认（L2/L3 必做，L1 可省）**：模块规划敲定后、进入第 3 步深读前，把「拟设模块清单 + 每模块一句话」发给用户看一眼——**非阻塞**：发出后即可继续推进，用户未响应视为确认；用户有异议则按意见调整规划再深读。这一步把"选错流程族"的方向性返工从交付后提到动工前（实证：真实生成中从选档到交付用户零交互，大纲单方敲定，方向错了要整课返工）。

**模块排序指引**：模块顺序可按认知坡度重排（小而具体的单元先行），不必机械跟随运行时序；凡重排处，必须在模块 header 用一句话显式说明与流水线时序的关系（正例："上一模块讲了『认字』，这一模块讲『取景』——与运行时序相反，先易后难"）。

## 第 2.5 步：创建隐喻分配表、术语定义表与测验溯源对照表

在写任何课程内容之前，建立三张表并全程维护（作为工作笔记跟随整个生成过程，不需要交付给用户）：

**隐喻分配表**（概念 → 隐喻）：

| 概念 | 隐喻 | 喻体关键词 | 用于哪个模块 |
|---|---|---|---|
| 数据库 | 带卡片目录的图书馆 | 图书馆、目录卡片 | 模块 3 |
| 认证 | 查身份证的保安 | 身份证 | 模块 4 |

**术语定义表**（术语 → 核心定义 → 上下文补充）：

| 术语 | 核心定义（全局不变） | 上下文补充（按模块微调） |
|---|---|---|
| middleware | 请求进入处理逻辑前的检查站 | 在本项目中，登录验证就在这里做 |

**测验溯源对照表**（测验 → 考察知识点 → 讲解位置）：第 7 步每出一道测验就登记一行，保证"先有讲解、后有测验"：

| 测验 ID | 考察知识点 | 讲解位置（模块 + 组件） |
|---|---|---|
| m1-q1 | localStorage 只能存字符串 | 模块 3 · 数据流动画第 3 站 + 翻译块 data-i=2 |

规则：

1. **先查重再使用**：每写一个新隐喻/新术语，先查表。**隐喻查重的单位是喻体关键词，不是概念**——同一喻体词不得用于两个不同概念（实证：'身份证'同时用作模板匹配与 MD5 记忆化的喻体即撞车）；同一概念的隐喻在其所属模块内的展开、结业回顾页复述、测验 `data-why` 回指均为合法。已用过的隐喻换新的，已定义过的术语沿用核心定义、只微调上下文
2. 同一术语在不同模块的解释必须沿用同一核心定义，只允许补充当前模块的具体作用——定义写进翻译块解释与测验 `data-why` 的正文里，保持全课一致
3. **测验必须可溯源**：第 7 步每出一道测验，先在对照表登记"考察知识点 + 讲解位置"；若该知识点在课程里**还没有对应讲解**，要么先补讲解模块、要么换题——禁止出现"只有测验、找不到讲解"
4. 多文件模式下，这三张表跨册共享，拆分前全局查重一次

## 第 3 步：架构级深读代码路径（四个子阶段）

对每个流程，**从第 1 步已验证的入口**开始，按下列子阶段分析。产出不只是"途经哪些文件"，而是能支撑测验与动画的结构化事实。

### 3a. 事件链与时序

- 沿调用链追到数据落点（数据库 / 文件 / API 响应），记录途经的每个文件与函数
- 识别异步环节：哪里排队、哪里重试、哪里会被丢弃；组件之间谁向谁发了什么消息
- 若流程由外部事件驱动（Webhook、用户操作、定时器），把触发 → 处理 → 反馈的完整时序列出来 → 这是探照灯（跨文件走读）与栈塔（调用/返回推演）的剧本，也是 §10b timeline 的数据

### 3b. 数据变形追踪

- 挑每个流程中**最重要的一条数据**，标注它在每一步的形态变化（如 `JSON 响应 → diff 字符串 → 处理后的数组 → 写库文档 → 页面显示对象`）
- 每次变形都要指认"谁动的手"（哪个函数做的 parse / filter / map / 截断）
- 这条变形链直接成为数据流动画的站点与 `flow-label` 文案，也是洋葱剥层（§4）的层次：**从最终形态剥回原始输入**，每层写清"谁动的手、丢了什么"
- 变形中**被丢弃的部分**（截断、过滤、默认值）往往是隐蔽 bug 的藏身处——在洋葱里做成"碎屑"让学习者亲手翻找，也值得出测验
- 顺手记录路径上的**真实数字**（超时时长、重试次数、阈值、大小上限、队列长度），并记下出处（哪个文件哪一行/哪个常量）——它们是第 6 步 §10 数据可视化图表（bars/timeline）的素材

### 3c. 错误边界与容错

- 遍历该流程路径上的错误处理（try-catch / 错误码 / 兜底默认值），归为两类：
  - **可恢复错误**（限流、超时、网络抖动——通常有重试或降级）
  - **不可恢复错误**（配置缺失、凭证无效——通常直接失败）
- 特别标出**静默失败点**：错误被吞掉、截断不报警、catch 后只打一行日志的地方
- 这一类事实是"用户反馈 X 现象，你会先查哪里"测验的最佳素材，也是因果赌注（§6）的标准赌局——在错误处理代码亮出之前，先让学习者押一注"这个异常是静默吞掉还是冒泡"

### 3d. 配置与扩展面

- 收集该流程读到的所有配置（env 变量 / 配置文件 / CLI 参数），分三类：**必选**、**可选调优**、**功能开关**
- 标注扩展点：想加一个同类新东西（新供应商 / 新规则 / 新字段），按现有抽象需要动几个文件、是否有现成接口可插
- 真实的分支点（`if / switch / 中间件条件`、策略选择）整理成参数 → 分支映射表 → 分叉沙盘（§11）的预标注数据；"为什么用策略模式而不是 if 堆叠"的取舍让学习者拖不同令牌亲手试出来
- 这直接支撑验收标准"学完能回答：加一个新功能该改哪些文件"，也是结业测验的出题来源

## 第 4 步：提取代码片段（**逐字复制，绝不改写**）

- 从真实文件中复制原始代码片段，一字不改（敏感信息脱敏与 HTML 实体转义是仅有的例外，见下）
- 记录每个片段的文件路径和行号范围
- 不许简化、不许重排、不许为了"好看"而调整格式
- 学习者必须能在仓库中打开文件，看到与课程完全一致的代码

### 转义铁律（唯一允许的"非改写"操作）

代码是纯文本，HTML 是标记语言——把前者放进后者，必须做**实体转义**，这不是改写：

- **规则**：嵌入 `<code>`/`<pre>` 前把 `&` → `&amp;`、`<` → `&lt;`、`>` → `&gt;`；放进属性值（如 `data-why`/`data-bet-why`）时 `"` → `&quot;`。四类 JSON 数据块（viz/onion/tower/fork）的字符串值内出现 `</script` 时写作 `<\/script`（JSON 合法转义，解析后字符不变），或拆开书写
- **判定标准**：浏览器渲染后的 **DOM 文本（textContent）**与源文件逐字一致即为合规；复制按钮读取的正是 textContent（app.js §1），转义后"复制即所得"完全不受影响
- **双向提醒**：源代码里本就有 `&amp;` 字面量时，`&` 要转义成 `&amp;amp;`——永远以"渲染出来的文本等于源文件"为准
- **不转义的后果**：被展示代码含 `<`、`</textarea>`、`onerror=`、`</script>` 时（HTML/JS 仓库几乎必然），轻则页面结构被代码内容破坏，重则恶意仓库埋入的 payload 在 file:// 下成为真实 XSS

### 纯 HTML 铁律（v1.11.1）

写入 HTML 文件的内容必须是纯 HTML，禁止一切 Markdown 语法混入。智能体的聊天回复、阶段报告可以用 Markdown，但只要落笔到 HTML（完整文档或片段），就只有 HTML：

- **禁令清单**：代码围栏 ``` / ~~~（含 ```html）、行内反引号对 `` `x` ``、行首 `#` 标题、行首 `-` / `*` 列表、`**加粗**`、`*斜体*`、`>` 引用、`[文字](地址)` 链接、`|---|` 表格分隔线
- **正确写法**：标题 `h1`–`h6`；列表 `ul`/`ol`/`li`；强调 `strong`/`em`；引用 `blockquote`；链接 `a href`；表格 `table`/`tr`/`td`；代码本来就该在 `pre`/`code` 里；留说明用 HTML 注释 `<!-- … -->`
- **边界**：`pre`/`code`/`script`/`style` 内的逐字内容除外——仓库源码本来就有 Markdown（如 README.md）时，按转义铁律原样展示，那是被展示的**数据**，不是页面**标记**
- **判定**：写出的文件浏览器直接打开正常渲染；交付前 `validate_course.py` 对正文（排除代码区）做 Markdown 标记机械扫描

## 第 5 步：写大白话翻译

为每个代码片段写逐段对应的通俗解释。遵循第 2.5 步的隐喻分配表，**用前先查重**。每个解释默认 1–2 句话；涉及关键机制或设计取舍时最多扩到 3 句，深讲必须落回代码（指认具体函数与变量），不许空谈理论。**例外**：设计取舍 / 机制展开段不受 3 句限（上限 6 句），但必须句句有信息增量且落到代码或配视觉/代码锚；普通叙述段仍按 1–3 句执行。

### 讲解深度底线（每个正式模块必须三层俱全，单文件与多文件同样适用）

"展示不要说教"限制的是**段落长度**，不是**讲解深度**。深度靠"多屏拆解 + 每屏配视觉"达成，而不是堆长文。每个正式模块（不含封面）必须依次回答三层问题，缺一层即为"简略层"返工：

1. **结构层——它住在哪**：本模块涉及的目录/文件在项目结构中的位置，与谁相邻、被谁调用。落地形式：§10a 目录职责导览图节点 + `.tp-file` 路径标注 + 探照灯站点的 `data-sp-file` 标注（目录职责一句话）
2. **机制层——核心模块各管什么**：该模块内每个核心模块（类/文件/子模块）的职责与关键设计取舍（为什么这样设计、换个做法会怎样）。落地形式：每个核心模块至少一个翻译块（代码 + 大白话），设计取舍用"为什么"短段落、测验的 data-why 或沙盘（§11）的分支试验承载
3. **流程层——来龙去脉**：关键流程不只列"途经哪些文件"，要讲清每一步**为什么走这里**：上一步的输出是什么形态、这一步对它做了什么、不做这一步会坏什么。落地形式：数据流动画的 `flow-label` 写数据形态、探照灯串起跨文件调用链、栈塔帧写真实调用与返回、§10b timeline 写真实先后与耗时

规模参照：**大型/复杂项目**（触发第 9 步拆分条件的，或核心目录 ≥10 个源文件的）每个流程族的讲解至少拆成 3 个正式模块（如"入口与调用链 → 核心机制 → 数据变形与落点"）；总览册必须含**目录结构导览**（§10a 文件数对比图标注每个目录职责）与**核心模块职责清单**（每个核心目录至少出现在目录职责图或翻译块中，不允许只列名字不讲作用）。

**主线锚点（L2/L3 长课必做）**：每个流程族的首模块 header 必须含一句从用户/操作者视角重连主线的话（正例："上一模块结束时，棋盘上公共区还剩 1 雷待定——现在把它讲完"）。模块内深讲允许切换到引擎视角，但族首必须回锚——长课中段最容易从"追一次操作"滑向"引擎教科书"，恰与体量峰值、参与式控件谷值三重叠加。

### 每模块内容量下限（不达标即为"简略层"，返工）

三层底线管的是"讲没讲到位"，本条管的是"给没给够料"——课程整体过简略，多半是每个模块都只给了"一张图 + 一句话"。下列数量为 **L2 标准档** 下限；L1 快览档允许低于此、L3 精讲档要求高于此（对照第 0 步档位参数表）。每个正式模块（不含封面）除三层俱全外，在 L2 档至少应具备：

- **至少 2 个代码翻译块**（`.translate-pair`），且模块涉及的每个核心目录/文件都至少有一段真实代码被逐字摘出并翻译——只列文件名、没给代码 = 简略
- **至少 1 个动画/参与式可视化**（数据流 / 探照灯 / 洋葱 / 栈塔 / 沙盘 / §10 图表）
- **至少 1 个应用型测验**（含 3 个以上选项，逐项带 `data-why`）
- **至少 2 种不同类型交互元素**
- **至少 1 处明确的设计取舍解释**（"为什么这样设计 / 换个做法会怎样"，用"为什么"短段落或测验的 `data-why` 承载）

一个模块内容过多、塞不下时，**拆成多个模块/多屏**，而不是压缩成一句概览。深度靠"多屏拆解 + 每屏配视觉 + 分段输出"共同达成（分段协议见 §8.0）。发现某模块无料可讲时，先回到第 3 步补深读（数据变形 / 错误边界 / 扩展面），再回来写，禁止用空话填充。

## 第 6 步：设计可视化

先按决策树为每个概念定性，再选形式：

```
这个概念的本质是什么？
├─ 数据在逐步变形、要看它经过哪里（原始输入 → 加工 → 落库）
│    → 数据流动画（§2）
├─ 调用链跨文件、要逐步走读"谁调用了谁"（3a 事件链）
│    → 执行探照灯（§3）
├─ 同一条数据的纵向演化：每层长什么样、谁动的手、丢了什么（3b 数据变形）
│    → 洋葱剥层（§4）
├─ 关键转折点要先预测再揭晓（3c 错误边界：吞掉还是冒泡？）
│    → 因果赌注（§6）
├─ 递归 / 回调 / 中间件链——"调用会再回来"的运行时纵深
│    → 栈塔（§12）
├─ 分支条件：不同输入走不同路（3d 配置扩展面、策略取舍）
│    → 分叉沙盘（§11）
├─ 概念背后有真实数据要对比（各目录文件数、行数、依赖数、错误分布）
│    → 数据可视化 · 条形对比（§10a bars）
├─ 一条事件链的时间先后与耗时（第 3a 步产物）
│    → 数据可视化 · 时间轴（§10b timeline）
├─ 状态机 / 算法步骤 / 队列逐帧演化
│    → 数据可视化 · 步骤回放（§10c steps）
├─ 代码本身的逐行含义
│    → 左右对照翻译块（§1）
└─ 以上都不贴切
     → 自定义可视化（见下方"不拘泥于既有形式"）
```

> **数字证据纪律（§10 数据可视化专用）**：图表里的每个数字都必须来自仓库真实可查数据——目录/文件数用实际清点结果、行数用实际读取统计、耗时用代码里的超时常量或注释数值、占比用实际统计。禁止编造、禁止把估算写成实测；每个数据项用 `anchor` 标注出处（如"清点自 src/ 目录"、"来自 package.json"、"src/queue.js L34 的 timeout"）。第 3 步深读时顺手把这些数字连同出处记下来。

**不拘泥于既有形式**——既有控件是默认起点和保底方案，不是上限。当代码的实际形态用控件表达不贴切时，应当为概念量身设计新形式。判断标准只有一个：**这个形式是不是为这个概念而生**。示例方向（仅为启发，鼓励原创）；标注 **§N** 的形式已由引擎内置，直接按 `interactive-elements.md` 对应小节用声明式模板实现，不必手写：

| 概念的实际形态 | 可量身设计的形式 |
|---|---|
| 分层过滤管道（中间件链、规则引擎） | 漏斗图：数据从上口进、每层筛掉一部分，旁注每层"拦下了什么"；也可以用 **§12 栈塔**逐帧压入中间件帧 |
| 状态机（订单状态、PR 生命周期） | **§10c steps**：逐帧回放状态迁移，点"下一帧"或自动播放 |
| 缓存命中/未命中 | **§11 沙盘**：拖不同请求令牌看它走快抽屉还是慢仓库；命中占比的对比用 **§10a bars** |
| 并发/竞态 | 两条并行跑道上的小球，重复点击"下单"看谁先到终点、谁的结果被覆盖 |
| 递归/树形结构 | **§12 栈塔**：递归调用亲手 push/pop，同一函数在栈里出现两次看得见；树形结构可做逐层展开动画 |
| 限流/背压 | **§11 沙盘**：拖观众令牌过旋转门，超过速率就被拒之门外 |
| 正则/模式匹配 | 输入框让学习者实时输入，看字符被高亮吞掉 |

自定义形式的工程约束（保证零依赖与懒播放不被破坏）：

1. **只许用原生 HTML + CSS + 内联 SVG + 原生 JS**，仍然零外部依赖
2. **接入懒播放**：自定义动画也要"滚入视口才开始演"——复用 `app.js` 预留的对外扩展点 `window.c2cLazyPlay(scene, play, stop)`（用法示例见 interactive-elements.md §13），或在课程内联脚本中用同样的 IntersectionObserver 结构；初始静止态用 CSS 类控制
3. **样式基于 base.css 变量**（`--accent`/`--accent-2`/`--bg-card` 等），保持视觉系统统一；自定义样式追加在 `<style>` 末尾
4. **贴冲突就回退**：如果自定义形式做出来还不如模板直观，就用模板——宁可用对形式，不用新形式
5. **数据驱动优先走引擎**：bars/timeline/steps（§10）与探照灯（§3）/洋葱（§4）/赌注（§6）/栈塔（§12）/沙盘（§11）能覆盖的概念直接用声明式模板（见 `interactive-elements.md`），不手写 JS；只有引擎覆盖不了的全新形态才允许手写
6. **安全白名单（手写 JS 硬边界）**：只允许操作 DOM/CSS、事件、定时器与 IntersectionObserver；**禁止** `fetch`/`XMLHttpRequest`/`WebSocket`、动态 `import()`、`location` 跳转与表单提交、`eval`/`new Function`、`document.write`、任何外链资源——课程是本地离线文件，任何网络请求与动态代码执行能力都是攻击面（对照 quality-gates.md 对应验收项逐条自查）

所有动画必须服务于理解。不为炫技而存在。同一模块至少搭配 2 种不同类型的交互元素。

## 第 7 步：编写应用型测验

每个模块结束时**至少一个测验**。测验考察"会不会做、懂不懂为什么"，不考记忆。

- ❌ 禁止："这个 API 叫什么名字？"、"哪个框架被使用了？"
- ✅ 要求："用户反馈切换页面后数据过期，你会先查哪里？"、"你想加收藏功能，需要改动哪些文件？"、"AI 生成的这段代码为什么会导致重复请求？"、"为什么这里用队列解耦而不是直接调用？"

用户选择答案后立即给出反馈和解释，解释要指出正确答案背后的代码依据。

**题干形态轮换**：预测输出题 / 改错题 / 排障题 / 加功能题轮换出题，连续 3 个模块不得使用同一题干形态；因果赌注可以充当某模块的收尾检验，替代部分常规测验——收尾节拍不要让学习者闭着眼都能预测。

**测验溯源纪律（对应第 2.5 步第三张表，逐题执行）**：

1. 出题前先问：这道题考察的知识点，课程里**讲过没有**？在对照表登记"测验 ID → 考察知识点 → 讲解位置（模块 + 组件）"后才算出题完成
2. 讲解位置必须是**具体可指认的**：某个翻译块、某个动画的某个站点、某个参与式控件（洋葱某层/栈塔某帧/沙盘某分支）或某段机制讲解——"整册大概讲到过"不算
3. 若发现考点没有对应讲解：**要么在对应模块补讲解（优先），要么换一道已讲解知识点的题**。禁止保留"裸测验"
4. 干扰项同样受约束：每个错误选项的 `data-why` 解释的机制，也应能在课程中找到依据（解释里指认的文件/函数必须已被或即将被讲解）
5. 交付前逐题回查对照表：任何一行"讲解位置"为空或指向不存在的内容，即为不合格项
6. `data-why` 里的前向模块指引须指向该知识点的主要讲解模块；课程外文档（README / 设计笔记）不得作为唯一机制依据。`data-why` 长度建议 ≤3 句，超长拆成"结论 + 指路"

## 第 8 步：组装最终 HTML

### 8.0 分段生成协议（防截断、保深度）

**本步产出体量远大于单次回复上限，禁止一次性写出整门课。** 分段生成既是防止"输出截断 → 交付半截课程"的硬约束，也是把课程真正做深的机制——有了分段，就再也不用为了"塞得下"而压缩讲解。协议如下：

**1. 分段粒度**

分段颗粒度随档位缩放（对照第 0 步档位参数表）：L1 快览档可 1–2 段覆盖整课（合并模块）、L2 标准档即下列规则、L3 精讲档在模块内再按"结构层/机制层/流程层"细分。下列为 L2 基准：

- 单文件课程：封面 + 每个正式模块各为一段；一个模块预计超过约 8–10 个组件（翻译块/动画/图表/测验）时，在组件边界拆成多段（先"结构层 + 机制层"、再"流程层 + 测验"等），每段仍是可独立粘入的完整 HTML 片段。
- 多文件课程：`index.html` 与每一册各为一段；册内再按模块细分。

**2. 拼接清单（每段必记，最终拼接的依据）**

分段前先立清单，边产出边回填：

| 文件 | 段序 | 模块 id / 锚点 | 承上启下（承接句/主线锚点） | 包含组件（翻译块/动画/图表/测验 id） | 代码片段（路径·行号） | 术语/隐喻 | 档位达标 | 源快照 | 状态 |
|---|---|---|---|---|---|---|---|---|---|
| course.html | 1 | #m0 封面 | — | .hero-stage + §10a 目录职责图 + 技术栈标签 + 规模行 | — | — | — | — | ✅ |
| course.html | 2 | #m1 添加待办 | 续封面导览"从一次真实点击开始" | 探照灯 + 翻译块×2 + 赌注 + 测验 m1-q1 | src/App.jsx·12-18 … | 便签本(React 状态) | L3：译块≥3？✅ | a1b2c3d | ✅ |

清单要点：

- 每段一行，段序即最终拼接顺序，绝不乱序
- 测验 id、术语、隐喻在清单里配合第 2.5 步三张表全局去重
- **档位达标列落盘即核对**（对照 §0 档位参数表：本段各模块的翻译块/测验/动画数量与分段粒度是否达到当前档位要求），每段写完立即回填本列，不达标**当场补**再标 ✅——交付前只做复核（实证：堆到交付前总核对，6/13 模块返工，还引发连带编辑事故）
- **承上启下列**登记本段承接句与主线锚点（流程族首模块必须有用户视角主线重连句）——并行分工时这一列就是工单的衔接信息，落盘即填
- **源快照列**记录被引代码的源仓库 commit hash（或快照目录）。源仓库在交付后仍会演进——没有基线，"逐字一致"事后无从复核（实证：交付两天后源仓库演进，84 块中 38 块行号漂移、14 块失配）
- 只有每一行的状态都为 ✅，才进入拼接；交付前再做一次总复核（双层核对）

**2.5 并行/分工生成的一致性对账（多会话/多工人场景必做）**

并行分段生成后，"数量核对"查不出"事实错误"——实证：某段 steps 动画把取点位置画成格子中心（照做必失败）、补装组件的隐喻漏登记、溯源表行号漂移，全部是"各段数量达标、事实互相矛盾"。因此：

- **三张表唯一事实源**：隐喻/术语/溯源三张表由主会话（或工头会话）持有，工人任务书从表生成，不允许各段自建
- **组件变更必须回报**：工人新增/改写组件（尤其验收期回补）时，同步回报隐喻登记与溯源表；补入/改写组件前对照同模块既有翻译块与图解核对关键事实，防止同一事实两种说法
- **终检以成品反向重建三张表**做双向 diff：从成品抽出全部组件与隐喻实例，与登记表逐条对账——多出来的查登记、少掉的查漏装
- steps/steps 类动画中的示意数值要么标"示意"，要么取真实值；涉及空间/物理的操作指引（点哪里、取哪个点）必须与同模块图解和代码语义核对

**3. 每段完整性的硬规则**

- 一段 = 一个或多个完整的 `<section class="module">…</section>` 块，内容齐全（含该模块所需的全部组件），可直接按段序粘入 `.content`。
- 一段写到一半发现接近输出上限：**在最近的组件边界收段**（已产出的组件保持完整），下一段**续写该模块剩余组件**；绝不允许用"省略剩余组件""把 3 个翻译块压成 1 个"的方式强行收尾。
- 段与段之间不重复输出 base.css / app.js——这两份只在最终拼接时各粘一次。

**4. 拼接顺序（所有段 ✅ 后执行）**

按下方"组装步骤"第 1–5 条执行，唯一区别是：**内容不是一次写出，而是按拼接清单段序把已完成的各段依次粘入**。粘完后补侧边栏 `.module-nav`（每个模块一个 `.nav-item[href="#id"]`，与 `.module` 一一对应），再做全局复查（见下方"组装步骤"第 5 条与 quality-gates.md 验收标准）。

**5. 可选：脚本化组装（大课推荐）**

段数多（≥8 段）或多册时，允许把各段先落盘为独立文件（`segments/m1.html`…），用一个零依赖小脚本按清单顺序拼接、并顺带跑机械检查（`{{` 残留、`http(s)://` 资源引用、data-i 配对、四类 JSON 可解析）——真实生成记录显示脚本化组装比人工粘贴更可靠（人工拼接收尾曾中断并重跑）。脚本组装后仍须走 quality-gates.md 全量验收；`validate_course.py`（技能根目录，可选）可直接复用。工程约束：

- 组装脚本建议支持 `--out`（输出路径，不直接覆盖成品）与 `--skill-root`（外壳来源目录）参数
- **外壳三件套随任务快照固定**：复制进工作目录或记录文件 hash，**禁止直接读取技能安装目录（如 ~/.agents/skills）的活动拷贝**——技能库升级会让重跑组装静默换壳
- **组装后 diff 校验**：重跑一次组装输出到临时文件，与交付成品 diff，零差异才标 ✅
- 写盘时保持换行符一致（LF/LF 或 CRLF/CRLF）：拼接脚本用文本模式写盘会把外壳的 LF 转成 CRLF，导致成品与外壳源文件"逐字一致"校验出现整文件假差异

## 第 9 步：大型项目 — 多文件拆分输出（条件触发）

**用户意愿优先**：如果用户明确要求单文件，即使超过下述阈值，也应尝试精简模块、压缩次要内容后仍出单文件，并向用户说明取舍；只有用户没有表态时才默认按下列条件判断。

**触发条件**（满足任一即拆分）：

- 代码库包含 **3 个以上独立运行的进程/服务**（如前端 Web + 后端 API + 后台任务队列；技术线示例：Web 前端、后端 API、后台任务、移动端、脚本工具、部署配置）
- 单个模块预计需要 **15 个以上代码片段**（比预估文件字节数更可靠）
- **体积参考线（量化护栏，按档位分层）**：L1/L2 单册 **>350KB** 建议评估拆分、**>500KB 红线**；**L3 精讲档上调为 >550KB 才强制评估、>700KB 红线**——外壳 125–130KB 打底 + L3 深讲内容超 350KB 是常态，对 L3 沿用 350KB 线只剩仪式价值（实证：460KB 的 L3 单文件课不拆是对的）。触线时先走**减重清单**再谈拆册：steps 帧的 SVG path 精简、viz JSON 的 note/anchor 长度上限、重复机制段合并、翻译块解释去重复——外壳约 125–130KB 是固定成本，超限时优先删减内容侧而非砍外壳。红线之上仍须拆分，或向用户说明取舍并获同意后才可交付单册
- 用户明确要求"分多个文件 / 按主题分开"

**拆分规则**：

1. **按用户操作流程或技术线分册**：一册 = 一个流程族（如 `01-overview.html`、`02-add-todo.html`、`03-persistence.html`）。绝不把一个流程的代码路径劈到两个文件里
2. **必须有一个 `index.html` 总目录页**：课程封面 + 全部分册卡片（`.volume-card`：分册名 + 一句话简介 + emoji），点击卡片以相对路径跳转。总目录页本身就是课程的第 0 屏，需符合视觉标准
3. **跨册导航，形式明确、不打断学习流**：
   - 每个分册**底部固定 pager**（`.pager`）："← 上一册 / 📖 目录 / 下一册 ↓"，始终可见
   - 分册页头显示当前册名 + 总目录链接，让学习者始终知道自己在哪一册
   - 分册内 ←/→ 键盘导航仍翻本册模块；翻到首/尾模块再按时，在进度条附近弹出**非阻断提示条**（`.vol-hint`，点击跳册、数秒自动消失），**禁止弹窗、禁止自动跳转**
4. **共享外壳，逐份内联**：每个 HTML 仍是自包含的——`resources/base.css` 与 `resources/app.js` **逐册复制内联**，禁止 `<link>` 外部 CSS 或共享 JS 文件。多文件 ≠ 多依赖，任意一册单独拷走仍能打开
5. **隐喻与术语全局唯一**：跨册共享第 2.5 步的三张表，拆分前先全局查重
6. **文件命名**：`index.html` + 两位序号短横线主题（`01-xxx.html`），全部小写，放在同一输出目录，交付时保持目录完整（如 zip）
7. **大型项目深度要求（防"薄册"）**：一册 = 一个流程族的**完整深讲**，不是概览分册。每册（总览册除外）至少 3 个正式模块，逐层满足第 5 步"讲解深度底线"的结构层/机制层/流程层；总览册必须含目录结构导览 + 核心模块职责清单（每个核心目录都被讲到位，而非一笔带过）。拆分的意义是把讲解做深——拆出来的每一册都应比"塞进单文件时的对应章节"更详细，而不是等量内容切成小块

**禁止**：

- 禁止用 iframe 套壳拼页
- 禁止任何一册引用另一册的 CSS/JS/资源
- 禁止把测验和它考察的代码拆到不同册
- 禁止"目录页式薄册"：某册除封面外只有 1–2 个模块、或模块里只有一张图/一个片段没有机制与流程讲解——这是"大型项目讲解停留在简略层面"的直接表现，按第 5 步深度底线补齐后再交付

## 第 10 步：交付后修订协议（课程迭代规则）

课程交付后用户要求"改一处 / 补一节 / 换个讲法"时，按本协议执行——局部修改最容易破坏的是全局不变量，必须按分类走对应动作，不许"只改用户指的那一行"。

**修订分类与动作**：

| 类型 | 典型请求 | 必做动作 |
|---|---|---|
| A. 局部文字/数值修正 | "这句话说错了""数字改成 42" | 只改目标位置；改了图表数字就同步核对 `anchor` 出处仍真实 |
| B. 代码片段更新（仓库变了） | "代码升级到新版本了" | 重新逐字提取 + 转义目标片段；核对 data-i 配对与行号标注；该片段若被测验/赌注引用，同步改题干与 data-why |
| C. 增删组件/模块 | "补一个赌注""删掉洋葱" | 更新拼接清单；侧边栏锚点与模块重新一一对应；增删测验必须回填/清除第 2.5 步溯源表 |
| D. 档位调整 | "整体升到精讲档" | 按 §0 切档规则重规划，已生成段按新档位重写/合并（含重写代价确认） |

**全局不变量复跑清单**（C/D 类修订后、重新交付前必查全部；A/B 类查相关项）：

1. 隐喻唯一：新增内容里的隐喻查分配表，与全课重复即换（或登记"零隐喻"）
2. 术语一致：沿用术语表核心定义，不同模块不各说各话
3. 测验溯源：新题登记讲解位置；被删讲解对应的题要么补讲解要么删题
4. 拼接完整性：模块 id ↔ `.nav-item` 一一对应，无残段、无截断组件
5. 机械检查照常：`{{` 清零、脱敏机检、四类 JSON 无裸 `</script`、转义抽检
6. 档位一致性：修订后全课仍与最终档位相符，无新老风格割裂
