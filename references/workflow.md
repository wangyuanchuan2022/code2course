# workflow.md — code2course 执行流程详解（第 0–9 步）

本文件是 SKILL.md「执行流程（分步总览）」的完整版。SKILL.md 只保留每步一句话，需要某一步的细节时按小节锚点加载本文件对应内容。**逐步执行，严格按序。**

> **证据纪律（贯穿第 1–4 步）**：所有分析结论必须锚定真实代码中的**文件名 + 函数名/类名/变量名**作为佐证。禁止"应该是"、"大概"式表述——每一个写进课程的说法，学习者都必须能翻到对应代码验证。这也正是测验"解释要指出正确答案背后的代码依据"的来源。

## 第 0 步：询问讲解档位（必问并等确认，随时可切）

在动工前必须先向用户提问选档并等待确认——**禁止默认、猜测或自动选择档位**。档位是**会话级全局参数**，控制全课的讲解精细度、信息密度、分段颗粒度与每模块内容量下限；生成过程中用户可随时切换（规则见本节末尾）。档位只改这四件事，不改其余硬约束。

### 档位参数表

| 维度 | L1 快览档 | L2 标准档 | L3 精讲档 |
|---|---|---|---|
| 定位 | 建立全局心智模型 | 吃透主要流程 | 逐文件逐函数吃透、可动手改 |
| 覆盖范围 | 1 个已验证入口 + 1–2 个最高频流程 | 第 2 步 3–5 个流程族，每族 1 个模块 | 第 2 步 3–5 个流程族，每族拆 2–3 个模块（结构/机制/流程分层） |
| 每模块代码翻译块 | 0–1 个 | ≥2 个（§5 内容量下限） | ≥3 个，每个核心目录/文件至少 1 段逐字代码 |
| 每模块动画/图表 | 1 个 | ≥1 个 | ≥2 个，§3 的 3a–3d 全部落地为内容 |
| 每模块测验 | 0–1 个 | ≥1 个（3+ 选项） | ≥2 个，含"加功能改哪些文件""为什么这样设计"深题 |
| 信息密度 | 低：术语只留核心、隐喻精简、不展开 3a–3d | 中：三层底线 + 关键取舍各 1 处 | 高：3a–3d 全展开、每个取舍给"为什么"、赌注/沙盘等参与式控件更密 |
| **每模块理解骨架（v1.18.0）** | 三句话卡 ×1 + 设计四问块 ≥1 + 结构/架构类图解 ≥1 | 三句话卡 ×1 + 设计四问块 **≥2** + 结构/架构类图解 ≥1 + 变量密集模块必配变量词典 | 三句话卡 ×1 + 设计四问块 **≥3** + 结构/架构类图解 ≥1 + 每个核心流程模块配变量词典与变量生命周期图 |
| **每模块交互元素种类** | 按需 | **按需**（v1.18.0 起：不再要求"≥2 种"；架构页/设计页优先） | 按需（可更密，但受 §6「交互克制原则」约束） |
| **结业改造指南（v1.18.0）** | ≥4 行 | **≥6 行** | ≥6 行，且覆盖换算法/换皮肤/禁某层/改通信四类 |
| 分段颗粒度 | 粗：1–2 段覆盖整课，模块合并为 3–5 屏 | 中：1 模块 = 1 段，过大按组件边界拆（§8.0） | 细：1 模块内按"结构层/机制层/流程层"再分多段 |
| 单/多文件 | 优先单文件 | 按 §9 条件触发 | 内容量大，更易满足 §9 拆分条件 |

> 表内数量是**该档位的最低要求/上限指引**；三档之间在讲解深度、信息密度、分段数量上必须拉开明显差距，禁止"三档都写成一样"。
>
> 档位数量下限同时是**机检事实源**：`validate_course.py --tier L1|L2|L3` 内置同表数值（脚本为准，本表为人读版）。"动画/图表 ≥N" 的计数口径 = 引擎组件（data-viz 三类 + 五个参与式控件场景）+ 手绘 SVG 图组。
>
> **v1.18.0 权力结构重排（治"装饰挤占架构"）**：可机检的**理解骨架**（总架构图 / 运行链路 / 三句话卡 / 变量词典 / 设计四问块 / 改造指南）进硬下限并由 `validate_course.py` 检查 19–23 把关；**交互元素"种类 ≥2"的下限取消，改为按需**——交互数量不再是达标手段，架构与设计才是。静态但承载理解的件**计入视觉与深度元素**（SKILL.md「视觉覆盖」同口径）。

### 选档与切档规则

1. **选档（激活时，必问）**：动工前必须主动向用户提问"用哪个档位：①快览档 ②标准档 ③精讲档？"并**等待用户确认**后才进入第 1 步。即使用户请求里已含档位词（"用快览档/标准档/精讲档""快速概览/精讲/逐行详解"等），也要复述确认（如"确认用精讲档，对吗？"），不得凭字面默认、猜测或自动选档；在收到明确确认前**不得开跑**。两条放宽：①**快速通道**——用户同一条消息里既有明确档位词、又有明确的开始指令时，复述确认后即可开跑，不必再空等一轮（用户随时可打断纠正）；③**角色桥接**——提问时可顺带问一句读者身份（audience.md 四画像），按其「角色 → 档位建议」对照表给建议，但**用户拍板，不代选**；④**无交互执行**（自动化流水线 / 子会话 / 用户明确"你定"三态之外无人应答）——允许自行取值，但必须**显式标注为缺省**：缺省取 **L2 标准档**，并在报告与产物里写明「按 L2 生成（无交互执行，未获用户档位确认）」，同时给出切档说明；这条是"绕过必问条款的登记机制"，不是"遵守"——事后仍须把档位决定回报用户。
2. **切档（生成中，随时）**：用户明确说"切到精讲档/切回快览档"等即生效；若用户只说"太细了/再详细点/简单点"等**未指明目标档位**，必须先问清切到哪一档，不得猜测。切换后：
   - **未生成的段**：立即按新档位重新规划分段粒度与每段深度（更新 §8.0 拼接清单）。
   - **已生成的段**：升档（L1→L2、L2→L3 等）时按新档位**重写**补足深度与组件；降档（L3→L2 等）时按新档位**合并精简**（删次要组件、合并模块/段）。切换时向用户一句话说明调整范围。
   - 切换**不推倒重来**：已完成的代码分析（第 1–4 步产物）与四张表（第 2.5 步）复用，只按新档位增减讲解深度与分段，不重新侦察仓库。
   - **重写代价确认**：切档涉及 ≥3 段或多册的重写/精简时，先向用户报一句预估改动范围（"约 5 屏要按精讲档回炉"），确认后再动手；小范围切换直接执行并一句话说明。
3. **档位只影响深度与分段**：代码逐字复制（含转义铁律）、隐喻唯一、数字可溯源、零依赖、外壳来自 resources、测验应用型等其余硬约束不因档位而变；讲解精细度、信息密度、分段颗粒度与每模块内容量下限随档位缩放——L1 允许低于 §5 标准下限，L3 要求高于标准下限。
4. **交付前复核档位一致性**：最终全课（含已重写段）的翻译块/测验/动画数量与分段粒度须与最终档位相符，无"前半精讲后半快览"的割裂（见 quality-gates.md）。
5. **冲突裁决规则（唯一优先级，防止两份刚性清单打架）**：通用内容下限条款（SKILL.md「视觉覆盖」、§5「每模块内容量下限」、quality-gates.md 对应验收项）与档位参数表冲突时，**一律以档位参数表为准**——L1 允许每模块 0–1 翻译块、0–1 测验、只 1 种交互元素；而零依赖、代码逐字（含转义）、隐喻唯一、数字可溯源、外壳来自 resources 等**完整性约束不接受任何档位豁免**。

## 第 1 步：物理拓扑与入口点映射

### 1a. 目录与依赖分层

- 浏览目录结构，识别主要语言、框架、构建工具
- 读 package.json / requirements.txt / go.mod 等依赖清单，并把核心依赖分两类：
  - **运行时强依赖**（缺了就跑不起来，如数据库驱动、Web 框架）
  - **可替换抽象层**（只是接口适配，换掉不影响核心逻辑，如某 LLM SDK、某云厂商 SDK）
- 这一层分类直接决定封面目录职责导览图怎么画、以及"换供应商要改哪里"类测验的答案

### 1b. 启动入口拓扑

- 列出**所有**可能的启动方式（Web 页面、CLI 命令、定时任务、Webhook 服务、CI Action……），不止第一个发现的
- 为每种方式标注对应入口文件，并**逐个验证**：
  - Web 应用：从 `index.html` / `main.*` / `app.*` 实际追到挂载点或启动调用，确认它真的被构建工具引用
  - CLI 工具：从 package.json 的 `bin` 字段或 argparse 入口确认
  - API 服务：从启动脚本（如 `server.js`、`manage.py runserver`）确认
  - 验证方法：入口文件中必须能找到"启动/挂载"的实际调用语句；找不到就换候选，直到闭环
- 确定这是"什么类型的应用"，以及**用户最可能从哪个入口进入**（它是课程第一模块的主角）

### 1c. 逻辑架构梳理（v1.18.0 新增：总架构图与运行链路的事实底稿）

1a 给的是**物理地图**（文件住哪），1b 给的是**入口清单**——两者都不回答"这个系统怎么运转"。本小步补上那个视角，产出**两种图**，它们是封面两件交付物（总架构图 `.arch-scene` + 一次完整运行链路 `.run-chain`）的事实底稿：

1. **对象从属/层次（谁拥有谁）**：从入口往下写"谁持有谁"，如 `main.py → PyQt5 UI / Solver`；`Solver → deduction / probability → vision → Windows/OpenCV`；`probability → native.py → mscore.cpp`。边语义用 `kind: "owns"`（持有/组成）或 `kind: "dependency"`（依赖）；
2. **一次运行的数据流与触发（含回边）**：从一次真实用户操作出发，写清"谁触发谁、传了什么形态的数据"，**结果回到界面的回边必须画出来**（如 `heatmap_signal → UI 更新`），不能只画向下的调用。边语义用 `kind: "call"` / `kind: "data"` / `kind: "control"`，回边照旧由引擎判定并画成强调色虚线；
3. **模块归属标注**：标出每个正式模块覆盖图上的哪一段（`module_marks[]`）——读者据此知道"为什么模块 4 突然讲 C++"（因为那是模块 3 的决策瓶颈）。**没有这层标注，读者只知道有五个模块，不知道它们在图上的边界**；
4. **一次完整运行的链路（对象级时序）**：另起一条链路图 `.run-chain`，如 `用户 → 点击「帮助」→ main.py → Solver.run() → vision.complete_scan() → deduction → probability → click → rescan_after_click() → heatmap_signal → Qt UI`，并配一句「后面每个模块只解释其中一段」。**结构图回答"由什么组成"，链路图回答"一轮怎么跑完"——两张都要，且都在开课处**（不是只在结业回顾）。

工程口径：节点的 `desc`（它做什么，业务向）、`role`（在系统里的角色）与边的 `kind`（owns/call/dependency/data/control）、`detail`（怎么依赖、如何调用、传什么）都是**要写进数据的必填语义**，不是可选修饰（契约见 interactive-elements.md §14/§15）。数据来源仍走 `analyze_structure.py` 结构事实（模块级聚合见「调用图前置」节），**诚实性契约不豁免**：图上每条边要么有 `file:line` 出处、要么标 `inferred`。


## 第 2 步：找出 3–5 个最常见的用户操作流程

问自己：真实用户打开这个应用后，最常做的 3–5 件事是什么？
例如：提交一个表单、加载一个列表页面、登录、搜索、点击某个按钮。
每个流程就是课程的一个候选模块。

**大纲轻确认（L2/L3 必做，L1 可省）**：模块规划敲定后、进入第 3 步深读前，把「拟设模块清单 + 每模块一句话」发给用户看一眼——**非阻塞**：发出后即可继续推进，用户未响应视为确认；用户有异议则按意见调整规划再深读。这一步把"选错流程族"的方向性返工从交付后提到动工前（实证：真实生成中从选档到交付用户零交互，大纲单方敲定，方向错了要整课返工）。

**模块排序指引**：模块顺序可按认知坡度重排（小而具体的单元先行），不必机械跟随运行时序；凡重排处，必须在模块 header 用一句话显式说明与流水线时序的关系（正例："上一模块讲了『认字』，这一模块讲『取景』——与运行时序相反，先易后难"）。

## 第 2.5 步：创建隐喻分配表、术语定义表、测验溯源对照表与变量词典（v1.18.0 四张表）

在写任何课程内容之前建立四张表并全程维护。前三张是**工作笔记**（跟随整个过程，不需要交付给用户），**第四张是交付物**——变量词典必须进课程正文（v1.18.0 起从"工作笔记"升格为读者查阅件，治"读者要在隐喻与变量之间来回翻译"）：

**隐喻分配表**（概念 → 隐喻 → 喻体关键词 → 映射到的具体变量/函数 → 用于哪个模块）：

| 概念 | 隐喻 | 喻体关键词 | 映射到的代码实体（v1.18.0 必填） | 用于哪个模块 |
|---|---|---|---|---|
| 数据库 | 带卡片目录的图书馆 | 图书馆、目录卡片 | `db.query()` · `cards` 表 | 模块 3 |
| 认证 | 查身份证的保安 | 身份证 | `verify_token()` · `session.user` | 模块 4 |

**术语定义表**（术语 → 核心定义 → 上下文补充）：

| 术语 | 核心定义（全局不变） | 上下文补充（按模块微调） |
|---|---|---|
| middleware | 请求进入处理逻辑前的检查站 | 在本项目中，登录验证就在这里做 |

**测验溯源对照表**（测验 → 考察知识点 → 讲解位置）：第 7 步每出一道测验就登记一行，保证"先有讲解、后有测验"：

| 测验 ID | 考察知识点 | 讲解位置（模块 + 组件） |
|---|---|---|
| m1-q1 | localStorage 只能存字符串 | 模块 3 · 数据流动画第 3 站 + 翻译块 data-i=2 |

**变量词典**（v1.18.0，**交付物**——进课程正文的 `.vardict-scene`，模板见 interactive-elements.md §15）：

| 代码变量 | 人话 | 生命周期（哪个阶段产生/消费/消亡） | 代码位置 |
|---|---|---|---|
| clicks | 外围候选格 | 分区阶段产生 | `utils/probability.py · L120` |
| click_list | 按约束关系分组后的候选格 | 拼桌阶段产生 | `utils/probability.py · L210` |

规则：

1. **先查重再使用**：每写一个新隐喻/新术语，先查表。**隐喻查重的单位是喻体关键词，不是概念**——同一喻体词不得用于两个不同概念（实证：'身份证'同时用作模板匹配与 MD5 记忆化的喻体即撞车）；同一概念的隐喻在其所属模块内的展开、结业回顾页复述、测验 `data-why` 回指均为合法。已用过的隐喻换新的，已定义过的术语沿用核心定义、只微调上下文
2. **隐喻预算（v1.18.0，S3）**：**同一模块内隐喻数量上限 3**；当某模块隐喻数 **≥ 该模块核心变量数的一半**时，**必须**用变量词典替代/压减隐喻，不得再加隐喻（治"隐喻已和真实变量一样多"）；每个隐喻除概念外**必须登记它映射到的具体变量或函数**（隐喻只映射到抽象概念 = 不合规）
3. **变量词典的触发与核对**：**核心变量 ≥5 的模块必配**（V 变量密集模块）；词典覆盖该模块的核心变量，**逐项回源码核对** `file:line`（不许凭记忆写位置）；读取路径上的核心变量若在代码里与用户给的直觉命名不一致，**以源码为准**并在结业或报告注明差异
4. 同一术语在不同模块的解释必须沿用同一核心定义，只允许补充当前模块的具体作用——定义写进翻译块解释与测验 `data-why` 的正文里，保持全课一致
5. **测验必须可溯源**：第 7 步每出一道测验，先在对照表登记"考察知识点 + 讲解位置"；若该知识点在课程里**还没有对应讲解**，要么先补讲解模块、要么换题——禁止出现"只有测验、找不到讲解"
6. 多文件模式下，这四张表跨册共享，拆分前全局查重一次

## 第 3 步：架构级深读代码路径（四个子阶段）

对每个流程，**从第 1 步已验证的入口**开始，按下列子阶段分析。产出不只是"途经哪些文件"，而是能支撑测验与动画的结构化事实。

**可选辅助：结构事实底稿 + 项目地图查询**——本步开工前，可先跑技能根目录的 `analyze_structure.py` 拿一份结构事实底稿（`python analyze_structure.py <目标仓库路径> --outdir <工作目录>/structure-facts`），产出 `structure-facts.json`（机器可读）与人读的 `structure-facts.md`（五件套：文件清单 / 符号表 / import 边 / 调用边 / 入口点 / 断点清单；支持 Python 及 C/C++/Java/C#/Go/Rust/PHP/Ruby/Kotlin/Swift/Scala/Dart/Lua/JS/TS）。拿到底稿后可以直接对它提问，不必手工翻文件：`map`（模块依赖地图）、`callers` / `callees <符号>`（谁调它 / 它调谁）、`impact <符号>`（影响半径）、`path <a> <b>`（调用路径）、`entry`（入口点）、`search <关键词>`。底稿里的边已按本步的边诚实性要求区分「实锤（带文件:行号）」与「推断」；`impact` 与 `path` 缺省只走实锤边。**这是可选的加速器，不是替代品——手工读码仍完全合法**；底稿与源码冲突时以源码为准（Python 走 ast 确定性提取，其余语言为表驱动启发式，已知盲区见底稿末尾的诚实性声明）。

**结构事实的正确用法（先看构成、再决定排除、最后才提问）**：底稿默认口径会把 vendored 第三方一起收进来，直接开查容易被第三方代码淹没（实证：某真实仓库 73.7% 符号来自内嵌的 pybind11 头）。顺序固定为三步——

1. **先看构成**：`map --depth 1` 看目录构成与符号分布；
2. **再排噪重跑**：底稿或 `map` 的 notes 出现「suspected vendored directory …consider re-running with --exclude X」时，用 `--exclude X` **重跑一次**再进入查询（工具只提示不自动排除——默认排除清单是冻结契约，且项目自己的 `include/` 不能替用户丢掉）；
3. **才开始提问**：`callers`/`callees`/`impact`/`path`/`search`。

读底稿时记住三条口径（底稿末尾诚实性声明同源）：

- **「实锤」标签分三级（看边上的 `resolved_by` 字段）**：实锤(名)=末段名在符号表唯一命中（或多候选经同文件唯一收窄）、实锤(绑定)=经 import 绑定收窄、实锤(限定)=限定名精确命中——都是"名字/绑定对上了"，不是"运行期确认"；导出到调用图时必须原样保留 verified/inferred 的区别；
- **跨 FFI 边界（pybind11 / ctypes / Cython / JNI）的调用静态不可见**：`native.mscore.win_rate(...)` 这类边会命中同语言同名符号自身——工具已把这类边（`self_ref` 标记）降级为「推断」，**画调用图时必须剔除 `self_ref: true` 的边**，否则会画出契约禁止的自环；
- **断点清单的「符号表未命中」有两义**：既可能是真外部/跨语言调用，也可能是本文件内的抽漏（启发式引擎不保证抽全）。落笔前对重要断点回源码核一眼；
- **`.h` 一律按 C 处理**（`.hpp`/`.hh`/`.hxx` 才是 C++）：header-only 或大量用 `.h` 写 C++ 的仓库，语言统计会记成 c，模板/命名空间语义按 C 口径——结论要按源码复核。

### 3a. 事件链与时序

- 沿调用链追到数据落点（数据库 / 文件 / API 响应），记录途经的每个文件与函数
- **调用边溯源（边诚实性）**：每条跨文件调用边落到「文件 + 行号」出处；凭命名相似/导入关系推测、未在源码里核实调用点的边，一律标注"推断"——后续讲解与可视化里同样区分（实锤边正常陈述，推断边注明"推断"），禁止把推断画成事实
- **跨 FFI 边界一律按"运行期绑定"处理**：Python↔C++（pybind11）、ctypes、Cython、JNI 等边界的调用**静态不可见**——结构事实里的「实锤」可能只是"和本语言同名符号撞了名"。凡调用点上出现 `模块.子模块.函数(...)` 形态（如 `native.mscore.win_rate(...)`）而调用者与 callee 同名时，一律按推断处理并**回源码人工核对**；把这类边画进调用图会产出契约禁止的自环（工具已用 `self_ref: true` 标出，见 §3 可选辅助与 interactive-elements.md §14d）
- **边诚实性引用依据（摘录 CodeGraph 源码原文，github.com/colbymchenry/codegraph，MIT License，2026-09 快照；见 `src/resolution/name-matcher.ts` 与 `src/graph/dynamic-boundary-report.ts`）**：
  1. "No fuzzy fallback, no qualified-name walking — a wrong callback edge is worse than none."（function_ref 消解的唯一或放弃纪律）
  2. "Reachability may reject a unique guess; it must never manufacture one."（可见性/可达性可以否决唯一候选，但绝不许反向制造一个）
  3. "silence beats a wrong edge"（完全连通的流程根本不会产出错误边——没有边好过有错边）
  三句同一条价值观：**宁缺毋错**。落到本技能：调用边收不窄就标"推断"、断点如实讲"断在哪里"，讲解与可视化里禁止为闭环硬造源码里不存在的边；工具侧的 `resolution`/`resolved_by`/`to_candidates`/`self_ref` 字段就是这三句话的机器可读形态。
- **半流程禁令**：一条流程链开讲就要闭环——从触发讲到数据落点；静态分析追不到的环节（动态分派、回调注册、事件总线）如实讲"断在哪里、为什么断、另一侧可能是什么"，禁止只演前半段让读者脑补，也禁止为闭环硬编源码里不存在的边
- 识别异步环节：哪里排队、哪里重试、哪里会被丢弃；组件之间谁向谁发了什么消息
- 若流程由外部事件驱动（Webhook、用户操作、定时器），把触发 → 处理 → 反馈的完整时序列出来 → 这是探照灯（跨文件走读）与栈塔（调用/返回推演）的剧本，也是 §10b timeline 的数据

### 3b. 数据变形追踪

- 挑每个流程中**最重要的一条数据**，标注它在每一步的形态变化（如 `JSON 响应 → diff 字符串 → 处理后的数组 → 写库文档 → 页面显示对象`）
- 每次变形都要指认"谁动的手"（哪个函数做的 parse / filter / map / 截断）
- 这条变形链直接成为数据流动画的站点与 `flow-label` 文案，也是洋葱剥层（§4）的层次：**从最终形态剥回原始输入**，每层写清"谁动的手、丢了什么"
- 变形中**被丢弃的部分**（截断、过滤、默认值）往往是隐蔽 bug 的藏身处——在洋葱里做成"碎屑"让学习者亲手翻找，也值得出测验
- 顺手记录路径上的**真实数字**（超时时长、重试次数、阈值、大小上限、队列长度），并记下出处（哪个文件哪一行/哪个常量）——它们是第 6 步 §10 数据可视化图表（bars/timeline）的素材

### 3c. 错误边界与容错

- 遍历该流程路径上的错误处理（try-catch / 错误码 / 兜底默认值），归为两类：
  - **可恢复错误**（限流、超时、网络抖动——通常有重试或降级）
  - **不可恢复错误**（配置缺失、凭证无效——通常直接失败）
- 特别标出**静默失败点**：错误被吞掉、截断不报警、catch 后只打一行日志的地方
- 这一类事实是"用户反馈 X 现象，你会先查哪里"测验的最佳素材，也是因果赌注（§6）的标准赌局——在错误处理代码亮出之前，先让学习者押一注"这个异常是静默吞掉还是冒泡"

### 3d. 配置与扩展面

- 收集该流程读到的所有配置（env 变量 / 配置文件 / CLI 参数），分三类：**必选**、**可选调优**、**功能开关**
- 标注扩展点：想加一个同类新东西（新供应商 / 新规则 / 新字段），按现有抽象需要动几个文件、是否有现成接口可插
- 真实的分支点（`if / switch / 中间件条件`、策略选择）整理成参数 → 分支映射表 → 分叉沙盘（§11）的预标注数据；"为什么用策略模式而不是 if 堆叠"的取舍让学习者拖不同令牌亲手试出来
- 这直接支撑验收标准"学完能回答：加一个新功能该改哪些文件"，也是结业测验的出题来源

## 第 4 步：提取代码片段（**逐字复制，绝不改写**）

- 从真实文件中复制原始代码片段，一字不改（敏感信息脱敏与 HTML 实体转义是仅有的例外，见下）
- 记录每个片段的文件路径和行号范围
- 不许简化、不许重排、不许为了"好看"而调整格式
- 学习者必须能在仓库中打开文件，看到与课程完全一致的代码

### 转义铁律（唯一允许的"非改写"操作）

代码是纯文本，HTML 是标记语言——把前者放进后者，必须做**实体转义**，这不是改写：

- **规则**：嵌入 `<code>`/`<pre>` 前把 `&` → `&amp;`、`<` → `&lt;`、`>` → `&gt;`；放进属性值（如 `data-why`/`data-bet-why`）时 `"` → `&quot;`。四类 JSON 数据块（viz/onion/tower/fork）的字符串值内出现 `</script` 时写作 `<\/script`（JSON 合法转义，解析后字符不变），或拆开书写
- **判定标准**：浏览器渲染后的 **DOM 文本（textContent）**与源文件逐字一致即为合规；复制按钮读取的正是 textContent（app.js §1），转义后"复制即所得"完全不受影响
- **双向提醒**：源代码里本就有 `&amp;` 字面量时，`&` 要转义成 `&amp;amp;`——永远以"渲染出来的文本等于源文件"为准
- **不转义的后果**：被展示代码含 `<`、`</textarea>`、`onerror=`、`</script>` 时（HTML/JS 仓库几乎必然），轻则页面结构被代码内容破坏，重则恶意仓库埋入的 payload 在 file:// 下成为真实 XSS

### 纯 HTML 铁律（v1.11.1）

写入 HTML 文件的内容必须是纯 HTML，禁止一切 Markdown 语法混入。智能体的聊天回复、阶段报告可以用 Markdown，但只要落笔到 HTML（完整文档或片段），就只有 HTML：

- **禁令清单**：代码围栏 ``` / ~~~（含 ```html）、行内反引号对 `` `x` ``、行首 `#` 标题、行首 `-` / `*` 列表、`**加粗**`、`*斜体*`、`>` 引用、`[文字](地址)` 链接、`|---|` 表格分隔线
- **正确写法**：标题 `h1`–`h6`；列表 `ul`/`ol`/`li`；强调 `strong`/`em`；引用 `blockquote`；链接 `a href`；表格 `table`/`tr`/`td`；代码本来就该在 `pre`/`code` 里；留说明用 HTML 注释 `<!-- … -->`
- **边界**：`pre`/`code`/`script`/`style` 内的逐字内容除外——仓库源码本来就有 Markdown（如 README.md）时，按转义铁律原样展示，那是被展示的**数据**，不是页面**标记**
- **判定**：写出的文件浏览器直接打开正常渲染；交付前 `validate_course.py` 对正文（排除代码区）做 Markdown 标记机械扫描

## 第 5 步：写大白话翻译

为每个代码片段写逐段对应的通俗解释。遵循第 2.5 步的隐喻分配表，**用前先查重**。每个解释默认 1–2 句话；涉及关键机制或设计取舍时最多扩到 3 句，深讲必须落回代码（指认具体函数与变量），不许空谈理论。**例外**：设计取舍 / 机制展开段不受 3 句限（上限 6 句），但必须句句有信息增量且落到代码或配视觉/代码锚；普通叙述段仍按 1–3 句执行。

### 讲解深度底线（每个正式模块必须三层俱全，单文件与多文件同样适用）

"展示不要说教"限制的是**段落长度**，不是**讲解深度**。深度靠"多屏拆解 + 每屏配视觉"达成，而不是堆长文。每个正式模块（不含封面）必须依次回答三层问题，缺一层即为"简略层"返工：

1. **结构层——它住在哪**：本模块涉及的目录/文件在项目结构中的位置，与谁相邻、被谁调用。落地形式：§10a 目录职责导览图节点 + `.tp-file` 路径标注 + 探照灯站点的 `data-sp-file` 标注（目录职责一句话）
2. **机制层——核心模块各管什么**：该模块内每个核心模块（类/文件/子模块）的职责与关键设计取舍。落地形式：每个核心模块至少一个翻译块（代码 + 大白话），**关键设计取舍一律落成「设计四问块」（`.design-qa`，v1.18.0 起为硬要求、每模块 ≥2 处、四问齐全）**——它做什么 → 为什么这么做 → **不这么做会怎样** → **为什么不用更简单的方法**。只写"为什么这样设计"一句不再合规：缺后果轴（不做会坏什么）与方案比较轴（为什么不用更简单的）就是把代码导览当成了工程理解（诊断见 v1.18.0 规格 R8）。测验的 `data-why` 与沙盘（§11）分支试验仍可作补充，但不能替代四问块
3. **流程层——来龙去脉**：关键流程不只列"途经哪些文件"，要讲清每一步**为什么走这里**：上一步的输出是什么形态、这一步对它做了什么、不做这一步会坏什么。落地形式：数据流动画的 `flow-label` 写数据形态、探照灯串起跨文件调用链、栈塔帧写真实调用与返回、§10b timeline 写真实先后与耗时

规模参照：**大型/复杂项目**（触发第 9 步拆分条件的，或核心目录 ≥10 个源文件的）每个流程族的讲解至少拆成 3 个正式模块（如"入口与调用链 → 核心机制 → 数据变形与落点"）；总览册必须含**目录结构导览**（§10a 文件数对比图标注每个目录职责）与**核心模块职责清单**（每个核心目录至少出现在目录职责图或翻译块中，不允许只列名字不讲作用）。

**主线锚点（L2/L3 长课必做）**：每个流程族的首模块 header 必须含一句从用户/操作者视角重连主线的话（正例："上一模块结束时，棋盘上公共区还剩 1 雷待定——现在把它讲完"）。模块内深讲允许切换到引擎视角，但族首必须回锚——长课中段最容易从"追一次操作"滑向"引擎教科书"，恰与体量峰值、参与式控件谷值三重叠加。

### 每模块内容量下限（不达标即为"简略层"，返工）

三层底线管的是"讲没讲到位"，本条管的是"给没给够料"——课程整体过简略，多半是每个模块都只给了"一张图 + 一句话"。下列数量为 **L2 标准档** 下限；L1 快览档允许低于此、L3 精讲档要求高于此（对照第 0 步档位参数表）。每个正式模块（不含封面）除三层俱全外，在 L2 档至少应具备：

- **至少 2 个代码翻译块**（`.translate-pair`），且模块涉及的每个核心目录/文件都至少有一段真实代码被逐字摘出并翻译——只列文件名、没给代码 = 简略
- **至少 1 个动画/参与式可视化，或 ≥1 张结构/架构类图解**（数据流 / 探照灯 / 洋葱 / 栈塔 / 沙盘 / §10 图表 / 本模块调用图 / 总架构图的这一片段）——**v1.18.0：静态结构图解与动效同权计入**，不再逼作者"为合规塞动效"
- **至少 1 个应用型测验**（含 3 个以上选项，逐项带 `data-why`）
- **理解骨架（v1.18.0 硬下限，机检 19–23）**：**三句话卡 ×1**（四行：解决什么问题/输入/输出/在总架构图上的位置）+ **设计四问块 ≥2 处**（L3 ≥3 处，每处四问齐全：它做什么／为什么这么做／不这么做会怎样／为什么不用更简单的方法）+ **变量密集模块（核心变量 ≥5）的变量词典**（含变量生命周期链）
- **交互元素种类：按需**（v1.18.0 取消"至少 2 种不同类型交互元素"的硬下限——**交互数量不再是达标手段**；架构页与设计页优先，不为凑数加动效。判定口径见 §6「交互克制原则」：删掉该动效后模块仍能理解 → 它不计入达标数）

一个模块内容过多、塞不下时，**拆成多个模块/多屏**，而不是压缩成一句概览。深度靠"多屏拆解 + 每屏配视觉 + 分段输出"共同达成（分段协议见 §8.0）。发现某模块无料可讲时，先回到第 3 步补深读（数据变形 / 错误边界 / 扩展面），再回来写，禁止用空话填充。

### 总架构图 + 调用图前置（封面双图 + 每个正式模块模块图，v1.14.0 起结构契约；v1.18.0 增总架构图与运行链路，机检把关）

课程给学习者的"地图"纪律：**开课先看全局与一次运行，进模块先看本模块的形状**。两套图分工明确——**总架构图回答"由什么组成、谁拥有谁、数据怎么流"**，**调用图回答"谁调谁"**，二者**并存**，不能互相替代（用户第一优先级反馈：只有目录地图与调用图 = 有地图没有架构）。

0. **封面（#m0）必配总架构图**（`.arch-scene`，v1.18.0 新增，复用调用图引擎）：一张图同时表达三层信息，**缺一层即不合格**——① 对象从属/层次（谁拥有谁，`kind:"owns"`）；② 一次运行的数据流与触发（`kind:"call"/"data"/"control"`，**含回边**：结果回到界面的边必须画出）；③ 模块归属标注（`module_marks[]` 标出每个正式模块覆盖哪一段）。节点 4–20、出处契约、`self_ref` 剔除、诚实性红线与调用图完全同源；节点必填 `desc`（它做什么）与 `role`（在系统里的角色），边必填 `kind` 与 `detail`（怎么依赖、如何调用、传什么）——**"图能看形状、不能看含义"是 v1.18.0 要治的缺陷**（契约与模板见 interactive-elements.md §14/§15）。
0b. **封面必配「一次完整运行」链路**（`.run-chain`，对象级时序 ≥4 步）：如 `用户 → 点击 → 入口 → 求解器 → 视觉 → 推理 → 决策 → 回写 → UI`，并配一句「后面每个模块只解释其中一段」。**结构图回答"由什么组成"，链路图回答"一轮怎么跑完"——两张都要，且都在开课处**（不是只在结业回顾）。
1. **封面（#m0）必配全项目调用图**：放一张**项目粒度**的调用图——节点用模块/文件级聚合（`kind: "module"` / `"file"` / `"entry"`，覆盖项目的主要子系统与入口），让学习者开课第一屏就看到整个项目的调用骨架。节点 4–20 契约**不豁免**：项目大就提高聚合粒度（目录级），不许把符号级全仓灌进封面。
2. **每个正式模块开头必配模块调用图**（不含封面与结业段）：该模块正文开始前，先放一张**本模块范围**的调用图（符号级，nodes = 本模块要讲的函数/方法），引子点明"这是封面全景图的哪一块"——模块图是全景图的放大镜，不是孤立新图。结业段豁免（与档位豁免同口径，由结业四件把关）。
3. **同源与出处纪律**：两张图的边一律来自 `analyze_structure.py` 的结构事实；模块级节点/边由符号级 facts 聚合派生——节点 `file` 填代表文件、`line` 填该文件首个符号声明行（"节点必须有出处"契约不豁免），边按节点归属聚合（`count` 累加、`confidence` 取最弱）。§14d SOP 与诚实性红线原样适用，`self_ref` 边照旧剔除；"两端末段名相同"的疑义边告警只针对符号级 id——路径形态 id（文件级/模块级节点，id 含 `/` 或末段为 `py`/`js` 这类扩展名）不参与该告警。
4. **机检**：`validate_course.py` 检查 17 核对"封面 ≥1 张调用图、每个正式模块 ≥1 张调用图"，检查 19 核对"封面 ≥1 张总架构图 + ≥1 条运行链路（≥4 步）"，检查 20–23 核对理解骨架其余四件（三句话卡/变量词典/设计四问块/改造指南）；缺位即 ERROR。
5. **模块入口四件的落位顺序**（v1.18.0）：进入正式模块，正文最前依次是**三句话卡 → 模块调用图 → 主线锚点句 →（其余组件）**——先声明边界与形状，再叙事。

## 第 6 步：设计可视化

先按决策树为每个概念定性，再选形式：

```
这个概念的本质是什么？
├─ 数据在逐步变形、要看它经过哪里（原始输入 → 加工 → 落库）
│    → 数据流动画（§2）
├─ 调用链跨文件、要逐步走读"谁调用了谁"（3a 事件链）
│    → 执行探照灯（§3）
├─ 同一条数据的纵向演化：每层长什么样、谁动的手、丢了什么（3b 数据变形）
│    → 洋葱剥层（§4）
├─ 关键转折点要先预测再揭晓（3c 错误边界：吞掉还是冒泡？）
│    → 因果赌注（§6）
├─ 递归 / 回调 / 中间件链——"调用会再回来"的运行时纵深
│    → 栈塔（§12）
├─ 系统由什么组成、谁拥有谁、数据怎么流（1c 逻辑架构）
│    → 总架构图（§15，三视图合一；封面必配）
├─ 一次运行从触发到回写的先后（1c 链路）
│    → 运行链路 .run-chain（§15；封面必配）
├─ 调用关系的整体形状：谁调谁、谁被最多人调、哪些边只是推断（结构事实）
│    → 调用图（§14）
├─ 分支条件：不同输入走不同路（3d 配置扩展面、策略取舍）
│    → 分叉沙盘（§11）
├─ 概念背后有真实数据要对比（各目录文件数、行数、依赖数、错误分布）
│    → 数据可视化 · 条形对比（§10a bars）
├─ 一条事件链的时间先后与耗时（第 3a 步产物）
│    → 数据可视化 · 时间轴（§10b timeline）
├─ 状态机 / 算法步骤 / 队列逐帧演化
│    → 数据可视化 · 步骤回放（§10c steps）
├─ 代码本身的逐行含义
│    → 左右对照翻译块（§1）
└─ 以上都不贴切
     → 自定义可视化（见下方"不拘泥于既有形式"）
```

> **数字证据纪律（§10 数据可视化专用）**：图表里的每个数字都必须来自仓库真实可查数据——目录/文件数用实际清点结果、行数用实际读取统计、耗时用代码里的超时常量或注释数值、占比用实际统计。禁止编造、禁止把估算写成实测；每个数据项用 `anchor` 标注出处（如"清点自 src/ 目录"、"来自 package.json"、"src/queue.js L34 的 timeout"）。第 3 步深读时顺手把这些数字连同出处记下来。

### 交互克制原则与复杂度护栏（v1.18.0，S4：治"讲代码的网页比被讲的代码还复杂"）

**正面原则写死：交互只解释复杂概念，不为简单概念增加交互。** 判断顺序是"这个概念值得交互吗"→"值得就用现成控件"，而不是"这个屏还没有动效、给它配一个"。

- **值得交互（白名单）**：调用链（探照灯/栈塔）、数据流（数据流/洋葱）、概率与推理过程、调用栈纵深、线程/进程通信、真实分支的条件选择。
- **不值得交互（一律用静态结构承载：表 / 架构图 / 三句话卡 / 四问块）**：目录介绍、简单变量解释、一眼能看懂的代码、单一事实陈述。
- **装饰性交互判定（可抽检口径）**：**删掉该动效后，这个模块还能被理解吗？能 → 该动效不计入达标数**——它的篇幅应当让给架构与设计（v1.18.0 之前这条被读成"动效不达标就要补动效"，方向正好相反：**不是补动效，是换架构**）。
- **复杂度护栏**：交付时除体积外，**另记录「交互组件总数」与「产物行数」**，写进交付报告；超出下列建议值时须说明取舍理由（与体积护栏同口径，**不为凑数而增件**）：交互组件总数建议 ≤ 模块数 ×4；单模块交互组件 >8 个时须在报告说明该模块为何需要。

**不拘泥于既有形式**——既有控件是默认起点和保底方案，不是上限。当代码的实际形态用控件表达不贴切时，应当为概念量身设计新形式。判断标准只有一个：**这个形式是不是为这个概念而生**。示例方向（仅为启发，鼓励原创）；标注 **§N** 的形式已由引擎内置，直接按 `interactive-elements.md` 对应小节用声明式模板实现，不必手写：

| 概念的实际形态 | 可量身设计的形式 |
|---|---|
| 分层过滤管道（中间件链、规则引擎） | 漏斗图：数据从上口进、每层筛掉一部分，旁注每层"拦下了什么"；也可以用 **§12 栈塔**逐帧压入中间件帧 |
| 状态机（订单状态、PR 生命周期） | **§10c steps**：逐帧回放状态迁移，点"下一帧"或自动播放 |
| 缓存命中/未命中 | **§11 沙盘**：拖不同请求令牌看它走快抽屉还是慢仓库；命中占比的对比用 **§10a bars** |
| 并发/竞态 | 两条并行跑道上的小球，重复点击"下单"看谁先到终点、谁的结果被覆盖 |
| 递归/树形结构 | **§12 栈塔**：递归调用亲手 push/pop，同一函数在栈里出现两次看得见；树形结构可做逐层展开动画 |
| 限流/背压 | **§11 沙盘**：拖观众令牌过旋转门，超过速率就被拒之门外 |
| 正则/模式匹配 | 输入框让学习者实时输入，看字符被高亮吞掉 |

自定义形式的工程约束（保证零依赖与懒播放不被破坏）：

1. **只许用原生 HTML + CSS + 内联 SVG + 原生 JS**，仍然零外部依赖
2. **接入懒播放**：自定义动画也要"滚入视口才开始演"——复用 `app.js` 预留的对外扩展点 `window.c2cLazyPlay(scene, play, stop)`（用法示例见 interactive-elements.md §13），或在课程内联脚本中用同样的 IntersectionObserver 结构；初始静止态用 CSS 类控制
3. **样式基于 base.css 变量**（`--accent`/`--accent-2`/`--bg-card` 等），保持视觉系统统一；自定义样式追加在 `<style>` 末尾
4. **贴冲突就回退**：如果自定义形式做出来还不如模板直观，就用模板——宁可用对形式，不用新形式
5. **数据驱动优先走引擎**：bars/timeline/steps（§10）与探照灯（§3）/洋葱（§4）/赌注（§6）/栈塔（§12）/沙盘（§11）能覆盖的概念直接用声明式模板（见 `interactive-elements.md`），不手写 JS；只有引擎覆盖不了的全新形态才允许手写
6. **安全白名单（手写 JS 硬边界）**：只允许操作 DOM/CSS、事件、定时器与 IntersectionObserver；**禁止** `fetch`/`XMLHttpRequest`/`WebSocket`、动态 `import()`、`location` 跳转与表单提交、`eval`/`new Function`、`document.write`、任何外链资源——课程是本地离线文件，任何网络请求与动态代码执行能力都是攻击面（对照 quality-gates.md 对应验收项逐条自查）

所有动画必须服务于理解。不为炫技而存在。同一模块至少搭配 2 种不同类型的交互元素。

## 第 7 步：编写应用型测验

每个模块结束时**至少一个测验**。测验考察"会不会做、懂不懂为什么"，不考记忆。

- ❌ 禁止："这个 API 叫什么名字？"、"哪个框架被使用了？"
- ✅ 要求："用户反馈切换页面后数据过期，你会先查哪里？"、"你想加收藏功能，需要改动哪些文件？"、"AI 生成的这段代码为什么会导致重复请求？"、"为什么这里用队列解耦而不是直接调用？"

用户选择答案后立即给出反馈和解释，解释要指出正确答案背后的代码依据。

**题干形态轮换**：预测输出题 / 改错题 / 排障题 / 加功能题轮换出题，连续 3 个模块不得使用同一题干形态；因果赌注可以充当某模块的收尾检验，替代部分常规测验——收尾节拍不要让学习者闭着眼都能预测。

**测验溯源纪律（对应第 2.5 步第三张表，逐题执行）**：

1. 出题前先问：这道题考察的知识点，课程里**讲过没有**？在对照表登记"测验 ID → 考察知识点 → 讲解位置（模块 + 组件）"后才算出题完成
2. 讲解位置必须是**具体可指认的**：某个翻译块、某个动画的某个站点、某个参与式控件（洋葱某层/栈塔某帧/沙盘某分支）或某段机制讲解——"整册大概讲到过"不算
3. 若发现考点没有对应讲解：**要么在对应模块补讲解（优先），要么换一道已讲解知识点的题**。禁止保留"裸测验"
4. 干扰项同样受约束：每个错误选项的 `data-why` 解释的机制，也应能在课程中找到依据（解释里指认的文件/函数必须已被或即将被讲解）
5. 交付前逐题回查对照表：任何一行"讲解位置"为空或指向不存在的内容，即为不合格项
6. `data-why` 里的前向模块指引须指向该知识点的主要讲解模块；课程外文档（README / 设计笔记）不得作为唯一机制依据。`data-why` 长度建议 ≤3 句，超长拆成"结论 + 指路"

## 第 8 步：组装最终 HTML

### 8.0 分段生成协议（防截断、保深度）

**本步产出体量远大于单次回复上限，禁止一次性写出整门课。** 分段生成既是防止"输出截断 → 交付半截课程"的硬约束，也是把课程真正做深的机制——有了分段，就再也不用为了"塞得下"而压缩讲解。协议如下：

**1. 分段粒度**

分段颗粒度随档位缩放（对照第 0 步档位参数表）：L1 快览档可 1–2 段覆盖整课（合并模块）、L2 标准档即下列规则、L3 精讲档在模块内再按"结构层/机制层/流程层"细分。下列为 L2 基准：

- 单文件课程：封面 + 每个正式模块各为一段；一个模块预计超过约 8–10 个组件（翻译块/动画/图表/测验）时，在组件边界拆成多段（先"结构层 + 机制层"、再"流程层 + 测验"等），每段仍是可独立粘入的完整 HTML 片段。
- 多文件课程：`index.html` 与每一册各为一段；册内再按模块细分。

**2. 拼接清单（每段必记，最终拼接的依据）**

分段前先立清单，边产出边回填：

| 文件 | 段序 | 模块 id / 锚点 | 承上启下（承接句/主线锚点） | 包含组件（翻译块/动画/图表/测验 id） | 代码片段（路径·行号） | 术语/隐喻 | 档位达标 | 源快照 | 状态 |
|---|---|---|---|---|---|---|---|---|---|
| course.html | 1 | #m0 封面 | — | .hero-stage + §10a 目录职责图 + §14 全项目调用图 + 技术栈标签 + 规模行 | — | — | — | — | ✅ |
| course.html | 2 | #m1 添加待办 | 续封面导览"从一次真实点击开始" | §14 模块调用图 + 探照灯 + 翻译块×2 + 赌注 + 测验 m1-q1 | src/App.jsx·12-18 … | 便签本(React 状态) | L3：译块≥3？✅ | a1b2c3d | ✅ |

清单要点：

- 每段一行，段序即最终拼接顺序，绝不乱序
- 测验 id、术语、隐喻在清单里配合第 2.5 步四张表全局去重
- **档位达标列落盘即核对**（对照 §0 档位参数表：本段各模块的翻译块/测验/动画数量与分段粒度是否达到当前档位要求），每段写完立即回填本列，不达标**当场补**再标 ✅——交付前只做复核（实证：堆到交付前总核对，6/13 模块返工，还引发连带编辑事故）
- **承上启下列**登记本段承接句与主线锚点（流程族首模块必须有用户视角主线重连句）——并行分工时这一列就是工单的衔接信息，落盘即填
- **源快照列**记录被引代码的源仓库 commit hash（或快照目录）**以及被引文件的 SHA256**。源仓库在交付后仍会演进——没有基线，"逐字一致"事后无从复核（实证：交付两天后源仓库演进，84 块中 38 块行号漂移、14 块失配）；而交付时工作区常带未提交改动，**commit hash 不足以复现逐字基线**（实证：交付时 `git status` 有 5 个 M 文件），故 hash 之外必须记被引文件的 SHA256（`Get-FileHash <文件> -Algorithm SHA256` 或 `sha256sum`），才能回答"当时引的到底是哪一版"
- 只有每一行的状态都为 ✅，才进入拼接；交付前再做一次总复核（双层核对）

**2.5 并行/分工生成的一致性对账（多会话/多工人场景必做）**

并行分段生成后，"数量核对"查不出"事实错误"——实证：某段 steps 动画把取点位置画成格子中心（照做必失败）、补装组件的隐喻漏登记、溯源表行号漂移，全部是"各段数量达标、事实互相矛盾"。因此：

- **四张表唯一事实源**：隐喻/术语/溯源/变量词典四张表由主会话（或工头会话）持有，工人任务书从表生成，不允许各段自建
- **组件变更必须回报**：工人新增/改写组件（尤其验收期回补）时，同步回报隐喻登记与溯源表；补入/改写组件前对照同模块既有翻译块与图解核对关键事实，防止同一事实两种说法
- **终检以成品反向重建四张表**做双向 diff：从成品抽出全部组件与隐喻实例，与登记表逐条对账——多出来的查登记、少掉的查漏装（变量词典是交付物，也在对账范围：词典里的 `file:line` 必须与成品一致）
- steps/steps 类动画中的示意数值要么标"示意"，要么取真实值；涉及空间/物理的操作指引（点哪里、取哪个点）必须与同模块图解和代码语义核对

**3. 每段完整性的硬规则**

- 一段 = 一个或多个完整的 `<section class="module">…</section>` 块，内容齐全（含该模块所需的全部组件），可直接按段序粘入 `.content`。
- 一段写到一半发现接近输出上限：**在最近的组件边界收段**（已产出的组件保持完整），下一段**续写该模块剩余组件**；绝不允许用"省略剩余组件""把 3 个翻译块压成 1 个"的方式强行收尾。
- 段与段之间不重复输出 base.css / app.js——这两份只在最终拼接时各粘一次。

**4. 拼接顺序（所有段 ✅ 后执行）**

按下方"组装步骤"第 1–5 条执行，唯一区别是：**内容不是一次写出，而是按拼接清单段序把已完成的各段依次粘入**。粘完后补侧边栏 `.module-nav`（每个模块一个 `.nav-item[href="#id"]`，与 `.module` 一一对应），再做全局复查（见下方"组装步骤"第 5 条与 quality-gates.md 验收标准）。

**5. 可选：脚本化组装（大课推荐）**

段数多（≥8 段）或多册时，允许把各段先落盘为独立文件（`segments/m1.html`…），用一个零依赖小脚本按清单顺序拼接、并顺带跑机械检查（`{{` 残留、`http(s)://` 资源引用、data-i 配对、四类 JSON 可解析）——真实生成记录显示脚本化组装比人工粘贴更可靠（人工拼接收尾曾中断并重跑）。脚本组装后仍须走 quality-gates.md 全量验收；`validate_course.py`（技能根目录，可选）可直接复用。工程约束：

- 组装脚本建议支持 `--out`（输出路径，不直接覆盖成品）与 `--skill-root`（外壳来源目录）参数
- **外壳三件套随任务快照固定**：复制进工作目录或记录文件 hash，**禁止直接读取技能安装目录（如 ~/.agents/skills）的活动拷贝**——技能库升级会让重跑组装静默换壳
- **组装后 diff 校验**：重跑一次组装输出到临时文件，与交付成品 diff，零差异才标 ✅
- 写盘时保持换行符一致（LF/LF 或 CRLF/CRLF）：拼接脚本用文本模式写盘会把外壳的 LF 转成 CRLF，导致成品与外壳源文件"逐字一致"校验出现整文件假差异

- 参与式控件键盘可操作：探照灯 ←/→ 逐站、洋葱 ←/→ 换圈 + Enter 剥层、栈塔 ←/→/↑/↓ 帧间移动、沙盘 ←/→ 推令牌；控件内方向键不触发模块翻页
- 结业收束段：最后一个正式模块之后设独立结业段并进入目录导航（模块 id 用 `m-finale` 或含 `finale`，如"13 · 结业"，**允许轻量**），必含**四件**（v1.18.0 起由三件升为四件）——全课主线回顾（优先可视化回放而非纯文字清单）+ 至少 1 道跨模块综合题 + 下一步行动指引 + **改造指南**（`.upgrade-guide`：常见修改任务 → 应该去哪（文件/模块）导航表，≥6 行真实任务，L1 ≥4 行；这是"从看懂到敢改"的落点，用户第⑤条第一优先级）；**收束段里的 mN 模块引用必须与各模块标题逐一核对**（实证：收束句把两个模块的职责写反，无任何机械校验兜住）
  - **机检口径（validate_course.py §11b + 检查 23，缺一即红）**：① id 含 `finale` 的段**豁免档位数量下限**（翻译块/引擎组件/测验都不再卡下限）；② 该段正文（代码样例不计）须出现「主线回顾」类词之一——`回顾/回放/回望/回主线/主线/串联/串起/串回/一条线/小结/总结/复盘/收束/贯穿`；③ 段内至少 1 个 `.quiz` 容器（跨模块综合题）；④ 正文须出现「下一步指引」类词之一——`下一步/接下来/继续/延伸/后续`；⑤（v1.18.0）段内至少 1 个 `.upgrade-guide`，`.ug-row[data-task]` ≥6 行（L1 ≥4）。写结业段时按这五个标记落笔即可一次过门（实证：不写固定措辞的"主线回放/串回一条线"会被判缺件）

### 8.1 交付报告与自评（v1.18.0，S4 复杂度护栏 + S5 交付自评表）

交付时除成品与体积记录外，报告里另附两样东西：

**① 复杂度护栏记录（S4）**：`交互组件总数`（引擎组件与参与式控件计数）+ `产物行数` + 体积。超出建议值（交互组件总数 > 模块数 ×4，或单模块交互组件 >8）时**必须写明取舍理由**——与体积护栏同口径，不许"为凑数而增件"，也不许默默超标。

**② 交付自评表（S5）**：把用户的评审维度变成交付前自检，逐项自评并写明依据（**分数不是门槛，但 <8 分的项必须给出补救说明或登记为遗留——无补救说明的低分项才算不合格**）：

| 维度 | 自查要点 |
|---|---|
| 信息准确性 | 说法与源码一致；无"应该是"式表述 |
| 代码溯源 | 每段代码有 `file · 行号`；跨文件调用边有出处或标"推断" |
| 运行链路 | 封面有「一次完整运行」链路，且各模块与链路对得上 |
| 模块划分 | 模块边界 = 用户流程族；无重复讲解、无漏讲的流程 |
| 交互教学 | 交互只用于复杂概念（§6 白名单）；删掉后模块仍能理解的动效已清理 |
| 架构总览 | 总架构图三视图齐全（层次/数据流与回边/模块归属）；模块卡与图对得上 |
| 新人上手效率 | 三句话卡 + 变量词典让读者不必来回翻译隐喻与变量名 |
| "为什么这样设计" | 每模块 ≥2 处设计四问块且四问齐全（含后果轴与方案比较轴） |
| 认知负担控制 | 隐喻 ≤3/模块；术语一致；篇幅与交互量不超标 |
| 整体完成度 | 分段拼接完整、机检全绿、档位一致 |

## 第 9 步：大型项目 — 多文件拆分输出（条件触发）

**用户意愿优先**：如果用户明确要求单文件，即使超过下述阈值，也应尝试精简模块、压缩次要内容后仍出单文件，并向用户说明取舍；只有用户没有表态时才默认按下列条件判断。

**触发条件**（满足任一即拆分）：

- 代码库包含 **3 个以上独立运行的进程/服务**（如前端 Web + 后端 API + 后台任务队列；技术线示例：Web 前端、后端 API、后台任务、移动端、脚本工具、部署配置）
- 单个模块预计需要 **15 个以上代码片段**（比预估文件字节数更可靠）
- **体积参考线（量化护栏，按档位分层）**：L1/L2 单册 **>350KB** 建议评估拆分、**>500KB 红线**；**L3 精讲档上调为 >550KB 才强制评估、>700KB 红线**——外壳 125–130KB 打底 + L3 深讲内容超 350KB 是常态，对 L3 沿用 350KB 线只剩仪式价值（实证：460KB 的 L3 单文件课不拆是对的）。触线时先走**减重清单**再谈拆册：steps 帧的 SVG path 精简、viz JSON 的 note/anchor 长度上限、重复机制段合并、翻译块解释去重复——外壳约 125–130KB 是固定成本，超限时优先删减内容侧而非砍外壳。红线之上仍须拆分，或向用户说明取舍并获同意后才可交付单册
- 用户明确要求"分多个文件 / 按主题分开"

**拆分规则**：

1. **按用户操作流程或技术线分册**：一册 = 一个流程族（如 `01-overview.html`、`02-add-todo.html`、`03-persistence.html`）。绝不把一个流程的代码路径劈到两个文件里
2. **必须有一个 `index.html` 总目录页**：课程封面 + 全部分册卡片（`.volume-card`：分册名 + 一句话简介 + emoji），点击卡片以相对路径跳转。总目录页本身就是课程的第 0 屏，需符合视觉标准
3. **跨册导航，形式明确、不打断学习流**：
   - 每个分册**底部固定 pager**（`.pager`）："← 上一册 / 📖 目录 / 下一册 ↓"，始终可见
   - 分册页头显示当前册名 + 总目录链接，让学习者始终知道自己在哪一册
   - 分册内 ←/→ 键盘导航仍翻本册模块；翻到首/尾模块再按时，在进度条附近弹出**非阻断提示条**（`.vol-hint`，点击跳册、数秒自动消失），**禁止弹窗、禁止自动跳转**
4. **共享外壳，逐份内联**：每个 HTML 仍是自包含的——`resources/base.css` 与 `resources/app.js` **逐册复制内联**，禁止 `<link>` 外部 CSS 或共享 JS 文件。多文件 ≠ 多依赖，任意一册单独拷走仍能打开
5. **隐喻与术语全局唯一**：跨册共享第 2.5 步的四张表，拆分前先全局查重
6. **文件命名**：`index.html` + 两位序号短横线主题（`01-xxx.html`），全部小写，放在同一输出目录，交付时保持目录完整（如 zip）
7. **大型项目深度要求（防"薄册"）**：一册 = 一个流程族的**完整深讲**，不是概览分册。每册（总览册除外）至少 3 个正式模块，逐层满足第 5 步"讲解深度底线"的结构层/机制层/流程层；总览册必须含目录结构导览 + 核心模块职责清单（每个核心目录都被讲到位，而非一笔带过）。拆分的意义是把讲解做深——拆出来的每一册都应比"塞进单文件时的对应章节"更详细，而不是等量内容切成小块

**禁止**：

- 禁止用 iframe 套壳拼页
- 禁止任何一册引用另一册的 CSS/JS/资源
- 禁止把测验和它考察的代码拆到不同册
- 禁止"目录页式薄册"：某册除封面外只有 1–2 个模块、或模块里只有一张图/一个片段没有机制与流程讲解——这是"大型项目讲解停留在简略层面"的直接表现，按第 5 步深度底线补齐后再交付

## 第 10 步：交付后修订协议（课程迭代规则）

课程交付后用户要求"改一处 / 补一节 / 换个讲法"时，按本协议执行——局部修改最容易破坏的是全局不变量，必须按分类走对应动作，不许"只改用户指的那一行"。

**修订分类与动作**：

| 类型 | 典型请求 | 必做动作 |
|---|---|---|
| A. 局部文字/数值修正 | "这句话说错了""数字改成 42" | 只改目标位置；改了图表数字就同步核对 `anchor` 出处仍真实 |
| B. 代码片段更新（仓库变了） | "代码升级到新版本了" | 重新逐字提取 + 转义目标片段；核对 data-i 配对与行号标注；该片段若被测验/赌注引用，同步改题干与 data-why |
| C. 增删组件/模块 | "补一个赌注""删掉洋葱" | 更新拼接清单；侧边栏锚点与模块重新一一对应；增删测验必须回填/清除第 2.5 步溯源表 |
| D. 档位调整 | "整体升到精讲档" | 按 §0 切档规则重规划，已生成段按新档位重写/合并（含重写代价确认） |

**全局不变量复跑清单**（C/D 类修订后、重新交付前必查全部；A/B 类查相关项）：

1. 隐喻唯一：新增内容里的隐喻查分配表，与全课重复即换（或登记"零隐喻"）
2. 术语一致：沿用术语表核心定义，不同模块不各说各话
3. 测验溯源：新题登记讲解位置；被删讲解对应的题要么补讲解要么删题
4. 拼接完整性：模块 id ↔ `.nav-item` 一一对应，无残段、无截断组件
5. 机械检查照常：`{{` 清零、脱敏机检、四类 JSON 无裸 `</script`、转义抽检
6. 档位一致性：修订后全课仍与最终档位相符，无新老风格割裂
7. **理解骨架完整（v1.18.0）**：增删组件或模块后复跑 `validate_course.py` 检查 19–23——封面总架构图与运行链路、每模块三句话卡、变量词典（含生命周期链）、设计四问块、结业改造指南；**删掉任何一件都要在同一修订内补回**（这类件最容易在局部修改中被"顺手删掉"而无机械兜底之外的提醒）

## 第 11 步：动态取证（选做阶段，v1.19.0）

前 10 步交付的是**静态理解**——"实锤"级的边来自源码消解，"推断"级的边只是猜测。本步骤回答一个更硬的问题：**这门课讲的运行链路，真的会被走到吗？** 做法是真实跑一次仓库（showcase），把执行轨迹采集成 trace-facts-v2，再与静态事实对齐。选做，但做了就要守本节的证据纪律。

**何时值得做**：仓库自带 examples / tests / benchmarks 中有"一条命令就能跑出主干行为"的入口（如 `--help`、一个最小 demo、一组单测）。找不到这种入口的仓库，本步骤直接跳过，不要硬造运行场景。

**采集命令模板**（python 仓 / node 仓各一条，产物都是 trace-facts-v2）：

```text
python -B trace_collect.py --repo-root <仓库根> --path <仓库根> [--out trace-facts.json] <入口命令及其参数>
node trace_node.mjs <仓库根> <入口脚本> --covdir <覆盖目录> [--port N | --url U] [--out trace-facts.json]
```

python 臂用 settrace 记 line + call 双事件（call 事件成对记录调用点→被调体，是**边级**证据）；node 臂走 V8 覆盖率，**没有 call 事件，edges 恒为空**——这是诚实置空，不是缺失。采集退出码：0 正常 / 2 用法配置错 / 3 目标进程崩了（部分轨迹仍落盘，可用但要注明）。

**三大坑（每个都踩过一次，照做免重踩）**：

1. **语料根禁 PYTHONPATH**：`--path` 目录必须插在 sys.path 的第一个 site-packages 条目**之前**（采集器已内置），绝不能用 PYTHONPATH 环境变量注入——它会污染子进程的解析顺序，采出来的轨迹是"另一个环境"的。
2. **junction 与 realpath**：Windows 上仓库路径经 junction/符号链接到达时，轨迹里的路径与静态分析里的路径可能字面不同——两侧都必须先 realpath 归一再比对（采集器与 align 都已内置），否则全量"文件不在轨迹中"假阴性。
3. **kill 不 flush V8**：node 臂若靠外部强杀结束目标进程，V8 覆盖率数据**不会写盘**（实测 covdir 0 文件）——必须让目标自己退出；采集器内置 grace/kill 阶梯（先给宽限期自退，超时才升级），采长驻服务时给它配一个"收到请求后自行退出"的入口或至少留足宽限。

**与静态事实对齐（align）**：

```text
python analyze_structure.py align --trace trace-facts.json --facts structure-facts.json --pkg <包名> [--out align.json]
```

轨迹 edges 非空（python 臂）时，align 把推断边与轨迹边**精确配对**（调用点行号 + 被调首行号），产出 `edge_measured`——这是"共执行"升级为**实测**的唯一合法路径（见下方铁律）。轨迹 edges 为空（node 臂）时只产出 `edge_upgrade_candidates`（共执行候选，不升档）。

**证据徽标三档**（写入课件时逐边标清，不得混用）：

| 徽标 | 含义 | 合法来源 |
|---|---|---|
| 实测 | 这条边被真实轨迹走到 | align 的 `edge_measured`（trace edges 精确配对），课件侧 `data-ev="measured"` + `data-ev-files` 声明证据文件，`validate_course.py --trace-facts` 机检锚定（检查 24） |
| 实锤 | 静态消解唯一命中 | analyze_structure facts 的 verified 边（name/binding/qualified 消解） |
| 推断 | 其余一切边 | facts 的 inferred 边；不得使用任何"实测"措辞 |

**共执行不升档铁律**：行级覆盖只能证明"两端代码在这次运行里都执行过"（共执行），**不能证明"这条边被走过"**——调用点在别处、动态分派、同名函数都能造出同型假象。因此共执行候选（`edge_upgrade_candidates`）**永不**把边升格为实测或实锤；课件与报告里引用共执行数字时必须写"共执行证据"，禁写"该边被实测走过"。唯一例外是上面的 align 精确配对路径。

**数据不足降级声明**：轨迹没采到的模块/边，课件侧必须降级——要么把"实测"徽标撤回为"实锤/推断"，要么在成品里显式写明"该环节未纳入本次运行取证"。宁可少一个实测徽标，不可让一个没有轨迹支撑的主张留在课件里（检查 24 会对无轨迹支撑的 `data-ev="measured"` 直接报错）。
